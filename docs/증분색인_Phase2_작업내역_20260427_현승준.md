## 3. 핵심 결정과 근거

### 3.1 기존 `sync_source` 는 LEGACY 로 보존, 신규 `enqueue_sync_job` 추가

설계서 §4 의 새 방식은 "워커가 chunk 단위로 처리" 인데, 기존 `DBIngestionService.sync_source()` 는 **호출 즉시 블로킹으로 전수 SELECT** 하는 흐름이다. 두 흐름은 비동기성·소요 시간·반환 형식이 모두 다르므로, **기존 함수를 신호 없이 행동만 바꾸면 호출자(스케줄러/관리자 API/v1 라우터)가 모두 깨진다**.

이를 피하기 위해:

- 기존 `sync_source(source_id, max_rows)` 는 그대로 둠 + 주석에 [LEGACY] 라고 명시
- 신규 `enqueue_sync_job(source_id, mode, trigger_type, reset_cursor)` 추가 — 즉시 반환, 워커가 처리
- 새 라우트 `POST /api/v1/admin/system/db/sources/{id}/enqueue` 가 enqueue 만 호출
- 기존 라우트 `/db/sources/{id}/sync` 는 그대로 LEGACY 동작 (호환성 보존)

스케줄러를 새 경로로 옮기는 작업은 별도 단계 (Phase 4 UI 마무리 시 함께)로 미뤘다. 한 번에 너무 많이 갈아엎지 않는다는 원칙을 따랐다.

### 3.2 `_migrate_add_missing_columns()` 헬퍼

기존 컨벤션(Alembic 미사용)을 유지하면서 컬럼 추가가 운영 환경에서 자동 적용되도록 `init_database()` 안에서 누락 컬럼만 ALTER TABLE ADD COLUMN 하는 헬퍼를 추가했다.

**왜 이렇게?**
- `Base.metadata.create_all()` 는 이미 존재하는 테이블의 신규 컬럼을 추가하지 않는다.
- 기존 환경에서 부팅 시 자동으로 컬럼이 채워지지 않으면 운영자가 수동 ALTER 를 따로 해야 하는데, 그 사이 워커가 컬럼 미존재로 죽는다.
- `inspect()` 로 누락된 것만 골라 ALTER 하므로 **반복 실행해도 안전(idempotent)** — 신규 환경/기존 환경 모두 동일 코드로 처리된다.
- DDL 실패는 부팅을 막지 않고 경고 로그만 남긴다 (권한 부족 등 운영 측 문제로 부팅이 통째로 실패하는 사고 방지).

검증:
- 신규 SQLite 환경 → `create_all` 한 번에 13+4=17 컬럼 다 생성
- Phase 1 시점 스키마(13컬럼)에 ALTER → 4 컬럼 추가 + 기존 row 데이터 보존 + NULL 채워짐
- 한 번 더 호출해도 깨지지 않음

### 3.3 엔진 캐시 (`db_engine_cache.py`)

설계서 §4.4 권장값을 그대로 따라:
- `pool_size=2, max_overflow=2, pool_pre_ping=True, pool_recycle=1800`
- `dict[source.id, Engine]` 프로세스 전역 캐시, double-checked locking 으로 thread-safe 보장
- `invalidate_engine(source_id)`: `upsert_source` 에서 connection_url 이 바뀌었을 때만 호출 (저작 변경 시 stale 커넥션 방지)
- `clear_all()`: 앱 종료 시 lifespan 에서 호출하여 모든 엔진 dispose

**왜 source.id 단위?**
- 같은 호스트라도 user/password/schema/query_text 가 다른 소스가 있을 수 있음 → URL 단위가 아닌 source 단위가 안전.
- 캐시 키가 단순(source.id) 해서 무효화 트리거가 명확.

### 3.4 쿼리 래핑 (`build_incremental_query`)

설계서 §4.2 의 SQL 을 그대로 구현:

```sql
SELECT * FROM ( {query_text} ) AS __src
WHERE __src.{cursor_column} > :cursor
ORDER BY __src.{cursor_column} ASC
LIMIT :chunk
```

**보안 결정**: `cursor_column` 은 `^[A-Za-z_][A-Za-z0-9_]*$` 화이트리스트로 검증.
바인드 파라미터로 처리할 수 없는 식별자(컬럼명) 부분이라 잘못 쓰면 SQL 인젝션 통로가 된다 — `id; DROP TABLE x` 같은 입력은 즉시 `ValueError`.

**Oracle 특수 처리**: Oracle 11g 이하는 `LIMIT` 미지원 → `db_type == "oracle"` 일 때만 `fetchmany(chunk)` 로 대체. SQLAlchemy 가 `LIMIT` 을 dialect 별로 변환해 주지만, 안전 마진 차원.

**첫 실행 (cursor 없음)**: WHERE 절 자체를 생략 → 전체 처음부터. cursor 가 빈 문자열일 때도 같은 분기.

**ORDER BY 필수**: cursor 진행을 보장하기 위해 cursor_column ASC 정렬 강제. 관리자가 등록한 query_text 의 ORDER BY 는 서브쿼리 안에서 무시될 수 있는데 — **그 점이 의도된 동작**이다 (외부 DB 측에 cursor_column 인덱스가 있어야 함은 설계서 §4.2 운영 주의사항).

### 3.5 `process_db_job` 의 트랜잭션 분리 전략

설계서 §4.5 의 "(d) chunk 처리 → cursor 갱신 + 카운터 누적 + lease 연장 (1 트랜잭션 commit)" 을 따르되, **외부 DB 작업과 로컬 DB 작업을 같은 트랜잭션에 묶지 않는다**:

| 단계 | 트랜잭션 |
|---|---|
| (a) Job + 소스 정보 로드 | 짧은 트랜잭션 1 (열고 닫음) |
| (b) 외부 DB chunk fetch | 외부 엔진 connection 만 사용, 로컬 DB 미접촉 |
| (c) `index_bulk()` (OpenSearch) | 로컬 DB 미접촉 |
| (d) 진행률 + cursor commit | 짧은 트랜잭션 2 (열고 닫음) |
| (e) lease 연장 | 짧은 트랜잭션 3 (renew_lease 안에서 자체 commit) |
| Job 종료 | cursor 승격 + last_error 갱신 + 이력 기록 — 각각 별도 짧은 트랜잭션 |

**왜 이 분리?**
- 외부 DB 응답 지연으로 로컬 DB 트랜잭션이 길게 잡히면 **lease 갱신 SQL 자체가 그 안에 갇혀버려** 데드락/락 대기가 발생할 수 있다.
- 로컬 DB 작업을 짧게 끊어두면, 다른 워커가 lease 만료 회수를 정상적으로 수행할 수 있다.
- 사용자가 강조한 "DB 커넥션 최소화" 원칙: chunk 1회 = 외부 1 connection + 로컬 1 짧은 connection 만 점유. 풀에 묶이지 않는다.

**chunk 단위 commit 의 의미** — chunk 도중 프로세스가 죽어도 마지막 chunk 까지의 cursor 가 DB 에 박혀 있으므로, 다음 워커가 lease 만료 회수 후 그 지점부터 재개. 설계서 §4.6 "장애 복구: 마지막 cursor 부터" 그대로.

### 3.6 PK 기반 Upsert

`_row_to_index_item()` 에서 `doc_id = f"{source.name}:{pk_value}"` 로 OpenSearch `_id` 생성. 같은 row 가 다시 색인되면 자동 덮어쓰기.

**효과** (설계서 §4.6 비교표):
- 기존: 로우마다 `find_duplicate_indexed_document()` 호출 → 100만 쿼리
- Phase 2: dup 체크 0회 (`index_bulk()` 가 dup 체크 안 함, PK 가 자동 처리)

### 3.7 동기화 이력은 기존 테이블 재사용

설계서 §4.5 "IndexingHistory / SmbSyncHistory 에 결과 요약 기록 (기존 경로 유지)" 에 따라, DB 색인 결과도 기존 `SmbSyncHistory` 테이블에 기록한다 (관리자 화면이 단일 화면이라 분리하면 UI 분기 부담만 늘어남).

**왜 SmbSyncHistory 인가** — 테이블명이 SMB 전용처럼 보이지만 컬럼 구성(`source_id, source_name, status, indexed, skipped, failed, trigger_type, message, started_at, finished_at, duration_ms`)이 source-agnostic 하다. 이름만 그렇지 의미는 "동기화 결과 요약" 이다. 테이블 rename 은 별도 마이그레이션 사고 위험이 있어 미루었다.

### 3.8 DB 커넥션 관점 — Phase 2 의 기여

| 지표 | 변경 전 | Phase 2 적용 후 |
|---|---|---|
| 외부 DB 엔진 생성 | sync 호출마다 `create_engine()` | source 별 1회, 이후 캐시 |
| 외부 DB SELECT | 매번 전수 | cursor 기준 chunk(500)씩 |
| 외부 DB connection 점유 | sync 1회 = 1 connection 길게 점유 | chunk 1회 = 짧게 점유 후 반환 |
| 로컬 DB 중복 체크 | row 마다 `find_duplicate_indexed_document()` | 0회 |
| 로컬 DB 트랜잭션 길이 | 외부 DB 응답 시간 포함 | chunk 직후 1회 짧은 commit |
| OpenSearch HTTP | row 1건당 1 호출 + refresh | 500건 묶어 1 호출, refresh 는 Job 종료 시 1회 |

## 4. 신규/변경 API 표면

### 4.1 관리자 API (`/api/v1/admin/system/`)

| 메서드 | 경로 | 권한 | 동작 |
|---|---|---|---|
| POST | `/db/sources` (수정) | operator | 4개 필드 추가 (`cursor_column`, `cursor_type`, `pk_column` + 기존) |

### 4.2 Pydantic 모델

`DbSourceRequest` 에 3 필드 추가:
- `cursor_column: str | None`
- `cursor_type: str | None` (int | datetime | string)
- `pk_column: str | None`

기존 폼은 누락해도 통과(`None` 기본). Phase 2 워커 경로를 쓰려면 3 필드 모두 채워야 enqueue 통과.

| DB 색인 이력도 `SmbSyncHistory` 테이블에 기록 | 화면 단일화 + 컬럼 호환 | 신규 `DbSyncHistory` 테이블 (탈락 — 테이블 분리만 늘리고 의미 동일) |
| sync-jobs 라우트는 admin 라우터에 통합 | 관리자 화면이 단일 admin 페이지 | 별도 `sync_jobs.py` 파일 (탈락 — 1:1 매핑이 깔끔) |
