### 3.1 `SyncJob` 테이블 신설

**위치**: [app/core/database.py:231](../app/core/database.py#L231)

설계서 §3.1 스키마를 그대로 따랐다. 기존 `IndexingHistory`/`SmbSyncHistory` 는 "결과 로그" 용도로 그대로 두고, `SyncJob` 은 "진행 중인 작업의 상태/체크포인트" 를 보관하는 별도 테이블로 분리했다.

**왜 별도 테이블?**

- 이력 테이블은 row-per-event(파일 1건 = 로우 1개) 구조이고, `SyncJob` 은 row-per-job(소스 동기화 1회 = 로우 1개) 구조라 의미가 다르다.
- 기존 이력 테이블에 컬럼을 우겨넣으면 lease/cursor/processed 같은 운영용 필드가 검색 통계와 섞여서 조회 성능에도, 의미 분리에도 좋지 않다.
- 설계서 §2 원칙 6 "기존 이력 테이블 보존" 을 그대로 반영.

**인덱스 설계**

- `ix_sync_jobs_status_created` (status, created_at): 워커가 가장 자주 치는 쿼리 — `status='pending'` 후보를 `created_at` 으로 정렬해서 1건 가져오는 패턴에 최적화.
- `ix_sync_jobs_source` (source_type, source_id): "이 소스에 다른 running Job 이 있는지" NOT EXISTS 검사용.

**마이그레이션**

기존 컨벤션에 맞춰 `init_database()` 의 `Base.metadata.create_all()` 로 자동 생성된다. 별도 Alembic 추가는 하지 않았다 (현재 프로젝트가 Alembic 미사용).
Phase 2/3 에서 `DbSource` / `FileIndexState` 에 컬럼을 추가할 때는 `create_all` 로는 처리되지 않으므로 별도 ALTER TABLE 처리를 같이 만들어야 한다 — Phase 2/3 작업 시 별도 다룬다.

### 3.2 `IndexingService.index_bulk()` 공통 메서드

**위치**: [app/services/indexing_service.py](../app/services/indexing_service.py) (`index_bulk`, `_build_doc_from_item`, `_embed_batch`)

#### 입력 계약

```python
items = [
    {
        "filename": "orders_12345.txt",   # 필수
        "text":     "본문 텍스트…",         # 필수 (호출자가 미리 추출)
        "doc_id":   "orders:12345",       # 선택 — OpenSearch _id (PK 기반 Upsert)
        "ext":      "txt",                # 선택
        "source_label": "db:my_source",   # 선택
        "content_hash": "...",            # 선택
        "indexed_at":   "ISO 시각 문자열",  # 선택
    },
    ...
]
IndexingService.index_bulk(items, index_name="cs_main", refresh=False)
```

#### 왜 이 형태?

설계서 §3.3 의 입력 시그니처(`items: list[dict]`, `skip_dup_check=True`) 를 그대로 따랐다.
다만 "skip_dup_check 플래그" 를 별도로 두지 않고, **호출자가 이미 변경분만 넘겨준다는 전제** 로 메서드 안에서 중복 체크 자체를 수행하지 않도록 만들었다. 이유:

- 설계서 §4.5 (DB) / §5.3 (SMB) 모두 호출 전에 변경 판별이 끝난 상태로 이 메서드를 호출하는 흐름이다.
- 같은 `_id` 로 재색인하면 OpenSearch 가 자동으로 덮어쓰므로(설계서 §3.3, §4.3) 별도 dup 체크가 불필요하다.
- 플래그를 두면 `skip_dup_check=False` 경로를 누가 어디서 쓸 거냐 라는 모호함이 남고, 결국 기존 `index_bytes()` 와 역할이 겹친다. **단일 함수가 명확한 책임 하나만 가지도록** 의도적으로 분리.
- 단일 파일 업로드 등 dup 체크가 필요한 경로는 기존 `index_bytes()` 를 그대로 쓴다.

#### 임베딩/색인 동작

- 임베딩은 `EMBED_BATCH_SIZE=32` 단위로 `model.encode(list, batch_size=...)` 호출. 설계서 §3.3 "임베딩 배치 (32~64건씩)" 의 하한을 채택. 메모리 안전 우선.
- OpenSearch 호출은 `_bulk` API. `BULK_CHUNK_SIZE=500` 단위로 끊어서 1회 HTTP 요청 = 500건 인덱스. 설계서 §4.6 의 "100만 건 → 약 2,000 호출" 계산과 동일.
- `refresh=False` 가 기본. 설계서 §3.3 "Job 완료 시점에만 명시적 refresh 1회" 를 호출자(워커 핸들러) 책임으로 둠. `index_bulk(..., refresh=True)` 로 마무리하면 1회 refresh 가 실행된다.

#### 실패 처리

- 임베딩 단계 전체 실패: 모두 failed 처리하고 즉시 반환.
- bulk 호출 자체 실패(네트워크/HTTP 에러): 해당 chunk 만 failed 카운트, 다음 chunk 는 계속 시도.
- bulk 응답 부분 실패: `resp["items"]` 로 항목별 검사, 성공/실패를 분리 카운트.

이 분리가 중요한 이유는 한 chunk 의 일부 문서가 매핑 충돌 등으로 실패해도 **전체 Job 을 멈추지 않게** 하기 위함이다. 설계서 §4.5 "장애 복구: 마지막 cursor 부터" 와 같은 원칙: 실패는 끊어내고, 진행 가능한 만큼은 진행시킨다.

#### `index_bytes()` 와의 관계

- `index_bytes()` 는 그대로 둠 (단일 파일 업로드 / 외부 호출자가 이미 사용 중).
- `index_bulk()` 은 워커 경로 전용. 추후 Phase 2/3 핸들러가 호출.
- 두 함수 모두 같은 `ensure_index()` 를 통해 동일 매핑 보장.

### 3.3 `IndexingWorker` (`app/services/worker_service.py`)

**위치**: [app/services/worker_service.py](../app/services/worker_service.py) (신규)

#### 핸들러 레지스트리 패턴

```python
# Phase 2/3 모듈이 import 시점에 호출
register_handler("db",  process_db_job)
register_handler("smb", process_smb_job)
register_handler("ssh", process_smb_job)
```

**왜 레지스트리?**

- Phase 1 단계에서 워커 인프라만 미리 합의하고 들어가면, Phase 2/3 작업 시 **인프라 코드를 다시 건드릴 일이 없다**. 설계서 §6 의 "공통 SyncJob / 공통 워커 큐" 원칙대로 인프라와 도메인 로직을 분리.
- 워커가 모든 도메인 모듈을 직접 import 하면 순환 import 위험이 생긴다. 핸들러는 **늦은 등록** 방식으로 회피.
- Phase 1 단독으로는 등록된 핸들러가 없으므로, 핸들러가 없는 source_type 의 Job 이 들어오면 즉시 `failed` + last_error 메시지("등록된 핸들러 없음...") 로 끊어낸다. 이렇게 하면 Phase 1 만 배포된 상태에서 누가 Job 을 만들어도 **테이블이 영원히 점유되는 일은 없다**.

#### `FOR UPDATE SKIP LOCKED` + Fallback

설계서 §3.2 의 SQL 을 그대로 가져오되, **두 가지 경로** 를 만들어 두었다.

1. **기본 경로** (`_claim_with_skip_locked`): PostgreSQL / MySQL 8+ / Oracle 에서 사용. `FOR UPDATE SKIP LOCKED` 로 동시성 처리.
2. **Fallback 경로** (`_claim_with_optimistic_update`): SQLite 등 SKIP LOCKED 미지원 환경. 후보 1건 SELECT 후 `WHERE id=? AND status=?` 조건부 UPDATE 의 `rowcount` 로 경합 해결.

분기 기준은 `settings.DB_TYPE` 으로 결정하되, **OperationalError 발생 시 자동으로 fallback 으로 영구 전환** 한다 (`self._supports_skip_locked = False`). 이유: MySQL 5.7 등 애매한 버전에서도 한 번의 실패로 자동 적응하도록 하기 위함. 첫 메시지에서 사용자가 SQLite 지원에 대해 답을 안 줬지만, 개발 환경 배려 차원에서 fallback 을 두는 것이 비용 대비 안전.

#### 소스당 동시 1 Job 제약

설계서 §5.7 의 SMB 보호 요구를 만족시키기 위해, 점유 SQL 자체에 다음 NOT EXISTS 절을 포함시켰다:

```sql
AND NOT EXISTS (
    SELECT 1 FROM sync_jobs r
    WHERE r.source_type = j.source_type
      AND r.source_id = j.source_id
      AND r.status = 'running'
      AND r.id <> j.id
      AND (r.lease_until IS NULL OR r.lease_until > :now)
)
```

이 제약을 워커 점유 단계에서 강제하면 **Phase 2/3 핸들러가 따로 신경쓸 필요가 없다**. DB 색인이든 SMB 색인이든 일관된 원칙이다.

#### Lease 관리

- 점유 시 `lease_until = now + lease_seconds` 로 셋팅 (기본 300초).
- 핸들러가 chunk 단위로 처리하다 lease 만료가 가까워지면 `IndexingWorker.renew_lease(job_id)` 호출로 갱신 (Phase 2/3 핸들러에서 사용 예정).
- lease 만료된 Job 은 다음 폴링에서 다른 워커가 회수 (설계서 §3.2 "죽은 워커 복구").

#### 종료 처리

- `done` / `failed` 시 `finished_at = now`, `lease_until = NULL` 로 정리. lease 를 비워야 다른 워커가 잘못 회수하는 일이 없다.
- `paused` 는 `lease_until` 만 비워 두고 status 를 그대로 유지 (사용자가 일시정지 → 재개 흐름).

#### 싱글톤

`IndexingWorker.start()` 는 프로세스 단위 싱글톤. lifespan 이 두 번 도는 사고 등으로 중복 호출돼도 안전하게 같은 인스턴스를 반환한다.

## 5. DB 커넥션 관점 — 무엇이 줄어드나

사용자가 거듭 강조한 "DB 커넥션 최소화" 관점에서, Phase 1 의 기여:

1. **워커가 점유하는 커넥션 수 = pool_size (기본 2)** 로 상한 고정. 폴링이 무한 spawn 되지 않는다.
2. **점유 SQL = 1 트랜잭션 / 1 커넥션** 으로 SELECT + UPDATE 끝. 후보 SELECT → 갱신 분리하지 않음.
3. `index_bulk()` 안에서는 OpenSearch 만 호출하고 **로컬 DB 는 단 1번도 건드리지 않는다**. 설계서 §4.5 의 "chunk 처리 → cursor 갱신 → lease 연장" 1 트랜잭션 commit 원칙을 Phase 2/3 에서 그대로 적용 가능.
4. `IndexingService.index_bulk()` 는 `DBService.find_duplicate_indexed_document()` 를 호출하지 않음 — 설계서 §4.6 의 "로컬 DB 중복체크: 100만 쿼리 → 0" 효과가 워커 경로에서 그대로 발생.

Phase 2/3 에서 이어서 줄어들 항목 (외부 DB cursor 기반 SELECT, FileIndexState 배치 UPSERT, 엔진 캐시) 은 다음 단계.

| `SyncJob` 별도 테이블 | 의미 분리 + 인덱스/조회 패턴 차이 | 기존 `IndexingHistory` 확장 (탈락) |
| `index_bulk()` 에서 dup 체크 미수행 | 호출자가 변경분만 넘긴다는 단일 책임 | `skip_dup_check` 플래그 (탈락) |
| 핸들러 레지스트리 | 인프라/도메인 분리 + 순환 import 회피 | 워커가 직접 import (탈락) |
| SQLite fallback 경로 추가 | 개발 환경 호환 + 미지원 DB 안전 | PostgreSQL only (탈락) |
| Alembic 미도입 | 현재 프로젝트 컨벤션 유지 | Alembic 신규 도입 (Phase 2/3 ALTER 시 재검토) |
| `EMBED_BATCH_SIZE=32` | 메모리 안전 우선 (설계서 32~64 하한) | 64 (운영 측정 후 상향 가능) |
| `BULK_CHUNK_SIZE=500` | 설계서 §4.6 기준 | 가변 (운영 측정 후 조정) |
