## 2. 항목별 상세 (Critical)

### C-1. 사용자 업로드 API 인증 누락 — A01: Broken Access Control
**문제**: `/api/v1/file/*` 레거시 라우트들(`upload`, `upload-sync`, `upload-multiple`, `document/{id}`, `search`, `read/{id}`)이 인증 없이 외부 노출.

**조치**:
- [main.py:include_router](../app/main.py) 단계에서 `dependencies=[Depends(require_role("operator"))]` 적용 (search 는 viewer)
- index 라우터는 X-Agent-Key 기반 `/agent-notify`, `/agent-check` 가 포함되어 prefix-level RBAC 와 충돌하므로 라우트별로 개별 RBAC 적용 (`/all-data` 에 viewer)

**효과**: 비인증 호출 즉시 401. 외부 노출 차단.

### C-2. 관리자 데이터 라우트 인증 누락
**문제**: `app/api/admin/index.py`의 `/all-data` 가 인증 없이 색인 전체 노출.

**조치**: `Depends(require_role("operator"))` 추가.

### C-3. 기본 시드 계정 자동 생성
**문제**: `_bootstrap_auth_seed`가 모든 환경에서 `admin/admin123!` 등 자동 생성.

**조치**:
- `APP_ENV in {prod, production}` 일 때 사용자 자동 시드 차단 (역할만 등록)
- 운영 첫 부팅은 `INITIAL_ADMIN_USERNAME` + `INITIAL_ADMIN_PASSWORD` 환경변수가 모두 명시된 경우에만 admin 계정 1명 생성, 동시에 `must_change_password=True` 로 강제 변경 유도
- dev/local/test 시드 계정에도 `must_change_password=True` 부여
- AuthUser 모델에 `must_change_password`, `last_password_changed_at`, `failed_login_count`, `locked_until` 컬럼 추가 + 마이그레이션

### C-4. 기본 SECRET 감지 강화 — A02: Cryptographic Failures
**문제**: `JWT_SECRET`/`CREDENTIAL_SECRET`/`OS_PASSWORD`/`DB_PASSWORD` 기본값 노출.

**조치**: 운영 환경 검증(`_validate_production_security`)에 다음 추가:
- `JWT_SECRET == 기본값 || len < 32` 차단
- `CREDENTIAL_SECRET == 기본값 || len < 32` 차단
- `DB_PASSWORD ∈ {cleversearch123, admin, changeme, password}` 차단
- `ALLOW_LEGACY_X_ROLE=true` 차단 (운영)

위반 시 부팅 자체 실패.

### C-5. ALLOW_LEGACY_X_ROLE 인증 우회 가능
**문제**: dev/local/test 에서 `X-Role: admin` 헤더만으로 admin 권한 획득.

**조치**: 기본값을 `false` 로 고정. 명시적으로 켜야만 동작. 운영 환경에 활성화되면 부팅 차단(C-4 와 연동).

### C-6. CSP `script-src-attr 'unsafe-inline'` 제거
**문제**: 인라인 onclick 등 DOM 속성 스크립트 허용 → XSS 위험.

**조치**: 모든 페이지(admin/일반/upload-sync) CSP 에서 `script-src-attr 'none'` 으로 변경. 외부 CDN(`cdn.tailwindcss.com`, `cdnjs.cloudflare.com`, `cdn.jsdelivr.net`, `unpkg.com`, `fonts.googleapis.com`, `fonts.gstatic.com`) 모두 제거 — 셀프 호스팅된 정적 자원만 사용.

## 3. 항목별 상세 (High)

### H-1. 외부 CDN + SRI 부재 — A08: Software and Data Integrity Failures
**조치**: C-6 와 함께 CSP 에서 외부 CDN 출처 일괄 제거. `static/vendor/` `static/fonts/` 의 셀프 호스팅 자원만 신뢰.

### H-2. PBKDF2 반복 횟수 부족
**조치**: [database.py:hash_password](../app/core/database.py)
```python
iterations = max(600_000, int(os.getenv("AUTH_PBKDF2_ITERATIONS", "600000")))
```
환경변수로 조정 가능, 최소값 600,000. 기존 200,000 해시는 다음 로그인 시 자연 마이그레이션 (검증은 저장된 iterations 사용).

### H-3. AES 키 도출 약함 + 키 회전 부재
**조치**: [crypto.py](../app/utils/crypto.py)
- `scrypt(secret, salt=결정적 salt, n=2^14, r=8, p=1, dklen=32)` 키 도출
- `enc:v2::` 버전 prefix — 신규 암호화는 v2, 복호화는 v1/v2 모두 지원하여 점진적 키 회전 가능

### H-4. 폐기 토큰 누적 / 성능 저하
**조치**: [security.py:cleanup_expired_revoked_tokens](../app/core/security.py)
- `expires_at < now()` row 일괄 삭제
- 5분 throttle (`_LAST_REVOKED_CLEANUP_AT`)
- 부팅 시 1회 강제 실행 (lifespan)

### H-5. 로그인 시도 제한 메모리 한정 — 분산/재시작 우회
**조치**: [security.py:authenticate_user](../app/core/security.py) 가 AuthUser 의 `failed_login_count`/`locked_until` 컬럼을 사용해 영속화. 5회 실패 시 15분 잠금 (환경변수 조정 가능).

### H-6. 인증서 갱신 스크립트 — 사용자 입력 제거
**조치**: [admin/system.py:generate_renew_script / run_renew_script](../app/api/admin/system.py) 가 더 이상 `script_path`/`output_path` 인자를 받지 않음. 고정 경로 `scripts/renew_certs.ps1` 만 사용.

### H-7. SSRF — connection_url 호스트 제한 가능
**조치**: [system_service.py:_validate_connection_url](../app/services/system_service.py)
- 허용 prefix 화이트리스트 (`postgresql+psycopg2://` 등)
- `DB_CONNECTION_ALLOWED_HOSTS` 환경변수에 명시된 호스트만 허용 (선택)
- `upsert_source` 와 `test_connection_url` 모두에서 검증 호출

### H-8. 의존성 버전 미고정
**조치**: [requirements.txt](../requirements.txt) 모든 의존성 `==X.Y.Z` 핀. 운영 가이드에 `pip-audit` / `safety check` CI 통합 명시.

### H-9. Zip bomb 검증 부재
**조치**: [upload_security_service.py:_is_valid_zip_family](../app/services/upload_security_service.py)
- `MAX_UNCOMPRESSED_BYTES = 200MB` 풀린 총 크기 한도
- `MAX_COMPRESSION_RATIO = 100` 압축비 한도
- 한도 초과 시 시그니처 검증 실패로 거부

## 5. 새 보안 정책 / 운영 가이드

### 5.1 환경변수 (운영 필수)

```env

JWT_SECRET=<32자 이상 강력한 무작위 문자열>
CREDENTIAL_SECRET=<32자 이상 강력한 무작위 문자열>
DB_PASSWORD=<강력한 비밀번호>
OS_PASSWORD=<강력한 비밀번호>
CORS_ALLOWED_ORIGINS=https://service.example.com
ENABLE_API_DOCS=false
OPENSEARCH_VERIFY_CERTS=true
ALLOW_LEGACY_X_ROLE=false   # (또는 미설정)

```

### 5.3 새 인증 흐름
```
[로그인]
  ↓ AuthUser.locked_until > now ? → 429 잠금 응답
  ↓ verify_password 실패 → failed_login_count++ (도달 시 locked_until = now+15m)
  ↓ 성공 → failed_login_count=0, locked_until=NULL
  ↓ JWT pair 발급 + cs_access_token / cs_refresh_token 쿠키
[API 호출]
  ↓ require_role 가 JWT 또는 access cookie 검증
  ↓ 폐기 토큰 테이블 조회 (만료 row 는 lifespan 시작 + 5분 throttle 로 자동 정리)
[로그아웃 / 토큰 만료]
  ↓ revoke_token → RevokedAccessToken/RevokedRefreshToken row 추가
  ↓ 만료 시각 도달 row 는 다음 cleanup 에서 삭제
```

### 5.4 새 암호화 흐름 (DB 접속 URL)
```
저장:
  raw → scrypt(CREDENTIAL_SECRET, 결정적 salt, n=2^14) → AES-256-GCM
       → "enc:v2::<base64(nonce|ciphertext)>"

복호화:
  prefix == "enc:v2::" → v2 키로 복호화 (정상)
  prefix == "enc::"    → v1 키로 복호화 (구버전 호환)
  prefix 없음          → 평문 그대로 (마이그레이션 호환)
```

키 회전 시: `CREDENTIAL_SECRET` 변경 → 모든 신규 저장은 v2(새 키), 기존 v1/v2 데이터는 운영 중 자연스러운 update 시 신규 키로 재암호화. 강제 회전이 필요하면 별도 스크립트로 모든 row 를 read→encrypt→write.
