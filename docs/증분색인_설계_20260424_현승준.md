- **작성일**: 2026-04-24

- **전제**: 온프레미스 환경 (외부 의존성 Redis/Celery 등 사용 불가)

## 1. 배경과 문제 정의

### 1.1 현재 동작
- **DB 색인** ([app/services/system_service.py:1207](../app/services/system_service.py#L1207)): 매 실행마다 `query_text` 전체를 `SELECT`. 로우마다 OpenSearch/DB에서 중복 확인 후 스킵.
- **SMB/SSH 색인** ([app/services/system_service.py:249](../app/services/system_service.py#L249)): 모든 파일에 `client.read_bytes()`를 호출한 뒤 해시를 계산하여 변경 여부 판단.
- **OpenSearch 색인** ([app/services/indexing_service.py:205](../app/services/indexing_service.py#L205)): `client.index(refresh=True)`로 1건씩 색인.

### 1.2 문제점
| 영역 | 문제 |
|---|---|
| DB 네트워크 | 매 실행마다 전수 SELECT → 대용량 테이블에서 외부 DB 부하 최대 |
| DB 로컬 비용 | 로우마다 `find_duplicate_indexed_document()` → 로컬 DB 쿼리 폭증 |
| SMB 네트워크 | 미변경 파일도 전부 다운로드 후 해시 비교 → 전송량 최대 |
| 로컬 상태 IO | 파일마다 개별 INSERT/UPDATE (`FileIndexState`) |
| OpenSearch | 1건당 1 HTTP 호출 + `refresh=True` → 처리량 제한 |
| 임베딩 | 로우/파일마다 직렬 호출 → CPU/GPU 활용률 저하 |
| 장애 복구 | chunk 단위 체크포인트 없음 → 중간 실패 시 처음부터 재시작 |
| 커넥션 비용 | DB 색인 실행마다 `create_engine()` → TCP 재연결 반복 |

## 2. 설계 원칙

1. **외부 의존성 없음**: FastAPI + SQLAlchemy + OpenSearch + smbprotocol/paramiko 만 사용
2. **원천 접근 최소화**: "이미 색인된 것은 원본에서 아예 가져오지 않는다"
3. **PK 기반 Upsert**: OpenSearch `_id`를 원본 PK로 고정하여 자동 덮어쓰기
4. **체크포인트 기반 재개**: 대용량 작업 중 장애 시 마지막 지점부터 이어서
5. **벌크 처리**: OpenSearch `_bulk` + 임베딩 배치
6. **기존 이력 테이블 보존**: `IndexingHistory`/`SmbSyncHistory`는 로그 용도로 유지, 증분 기준은 별도 컬럼에 관리

## 3. 공통 인프라

### 3.1 SyncJob 테이블 (DB 기반 작업 큐)

`app/core/database.py`에 신규 추가:

```python
class SyncJob(Base):
    __tablename__ = "sync_jobs"
    id = Column(Integer, primary_key=True)
    source_type = Column(String(16))          # "db" | "smb" | "ssh"
    source_id = Column(Integer)
    status = Column(String(16))               # pending | running | done | failed | paused
    mode = Column(String(16))                 # "incremental" | "full"
    cursor_value = Column(Text)               # DB: pk 값 / SMB: 마지막 파일 경로
    total_estimated = Column(BigInteger, nullable=True)
    processed = Column(BigInteger, default=0)
    indexed = Column(BigInteger, default=0)
    skipped = Column(BigInteger, default=0)
    failed = Column(BigInteger, default=0)
    worker_id = Column(String(64), nullable=True)
    lease_until = Column(DateTime, nullable=True)
    last_error = Column(Text, nullable=True)
    trigger_type = Column(String(16))         # manual | schedule | boot
    created_at = Column(DateTime)
    updated_at = Column(DateTime)
    started_at = Column(DateTime, nullable=True)
    finished_at = Column(DateTime, nullable=True)
```

### 3.2 IndexingWorker (프로세스 내부 스레드 풀)

`app/services/worker_service.py` 신규:

- 서버 기동 시 lifespan에서 `IndexingWorker(pool_size=2).start()` 1회 호출
- 폴링 주기 3초, lease 5분
- Job 점유는 `FOR UPDATE SKIP LOCKED`로 동시성 제어 (PostgreSQL/MySQL 8+)
- lease 만료된 Job은 다른 워커가 자동 회수 (죽은 워커 복구)

```sql
UPDATE sync_jobs
SET status='running', worker_id=:wid,
    lease_until = :lease_until, started_at = COALESCE(started_at, :now),
    updated_at = :now
WHERE id = (
    SELECT id FROM sync_jobs
    WHERE status='pending' OR (status='running' AND lease_until < :now)
    ORDER BY created_at ASC
    LIMIT 1 FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

### 3.3 IndexingService.index_bulk()

`app/services/indexing_service.py`에 신규 메서드:

- 입력: `items: list[dict]`, `index_name: str`, `skip_dup_check: bool = True`
- 임베딩 배치 (32~64건씩) → OpenSearch `_bulk` (refresh=False)
- Job 완료 시점에만 명시적 refresh 1회
- `skip_dup_check=True`일 때 기존 `find_duplicate_indexed_document()` 호출 생략

### 3.4 관리자 UI

[static/admin/indexing.html](../static/admin/indexing.html)에 추가:
- `GET /api/admin/sync-jobs` → 실행 중/대기 Job 목록
- 진행률 바: `processed / total_estimated`
- 버튼: **일시정지** (`status='paused'`) / **재개** (`status='pending'`) / **전체 재색인** (cursor 리셋 + `mode='full'`)

## 4. DB 색인 상세 설계

### 4.1 DbSource 스키마 확장

`app/core/database.py`의 `DbSource`에 추가:

```python
cursor_column = Column(String(128))       # 증분 기준 컬럼 (예: "id", "updated_at")
cursor_type = Column(String(16))          # "int" | "datetime" | "string"
last_cursor_value = Column(Text)          # 마지막 색인 완료 지점
pk_column = Column(String(128))           # OpenSearch _id 생성용 PK 컬럼
```

### 4.2 쿼리 래핑

관리자가 등록한 원본 `query_text`는 수정하지 않고 서브쿼리로 감쌈:

```sql
SELECT * FROM ( {query_text} ) AS __src
WHERE __src.{cursor_column} > :cursor
ORDER BY __src.{cursor_column} ASC
LIMIT :chunk
```

- `cursor_column`은 외부 DB에 **인덱스가 반드시 존재**해야 함 → UI에 경고 문구 표시
- `cursor_type`이 `datetime`일 경우 시계차 보정 위해 overlap 여유 1분 적용 가능 (옵션)

### 4.3 PK 기반 Upsert

```python
doc_id = f"{source.name}:{row[source.pk_column]}"     # 예: "orders:12345"
os_client.index(index=target_index, id=doc_id, body=doc, refresh=False)
```

- 같은 `_id`로 재색인하면 OpenSearch가 자동 덮어쓰기
- 별도 "UPDATE API" 호출 불필요, `_bulk`에서도 동일하게 동작

### 4.4 엔진 캐시

```python
# app/services/db_service.py (또는 신규 모듈)
_engine_cache: dict[int, Engine] = {}

def get_cached_engine(source: DbSource) -> Engine:
    if source.id not in _engine_cache:
        _engine_cache[source.id] = create_engine(
            _decrypt(source.connection_url),
            pool_size=2, max_overflow=2,
            pool_pre_ping=True, pool_recycle=1800,
        )
    return _engine_cache[source.id]
```

### 4.5 Chunk 단위 처리 흐름

```
1) SyncJob 생성 시 cursor_value = DbSource.last_cursor_value (이전 실행의 최종값)
2) Worker가 Job 점유
3) 루프:
   a) fetch_next_chunk(engine, source, cursor, CHUNK)
   b) 임베딩 배치 생성
   c) index_bulk() 호출 (PK 기반 Upsert)
   d) SyncJob.cursor_value 갱신 + processed/indexed 누적 + lease 연장 (1 트랜잭션 commit)
   e) time.sleep(0.05)  # 부하 제어
4) 결과 rows가 비면 Job 완료 → DbSource.last_cursor_value ← SyncJob.cursor_value 승격
5) IndexingHistory / SmbSyncHistory에 결과 요약 기록 (기존 경로 유지)
```

### 4.6 100만 건 기준 부하 비교

| 지표 | 현재 | 개선 후 |
|---|---|---|
| 외부 DB 전송 | 100만 로우 (매 실행) | 신규/수정분만 |
| 외부 DB 커넥션 | 실행마다 생성 | 엔진 캐시 재사용 |

## 5. SMB/SSH 색인 상세 설계

### 5.1 FileIndexState 스키마 확장

`app/core/database.py`의 `FileIndexState`에 추가:

```python
mtime = Column(DateTime, nullable=True)                     # 원격 파일 수정 시각
last_seen_at = Column(DateTime, nullable=True)              # 최근 walk 관찰 시각
os_doc_id = Column(String(64), nullable=True)               # OpenSearch 문서 ID

# 인덱스 추가
Index("ix_file_state_src", "source_type", "source_name")
```

### 5.2 walk() 시그니처 확장

`app/utils/smb_client.py` / `app/utils/sftp_client.py`:

```python
def walk(self, allowed_extensions=None) -> Iterator[FileEntry]:
    # 기존: (rel_path, full_path)
    # 변경: FileEntry(rel_path, full_path, size, mtime)
    yield FileEntry(rel_path=..., full_path=..., size=stat.size, mtime=stat.mtime)
```

- smbprotocol: `Open().create()` 후 `query_info()`로 메타만 획득 (read_bytes 호출 없이)
- paramiko SFTP: `listdir_attr()`로 size/mtime 일괄 조회

### 5.3 3단계 필터 (네트워크 최소화 핵심)

```
단계 1: client.walk() → 메타데이터(size, mtime)만 스트리밍
단계 2: 로컬 file_index_states 전체를 Job 시작 시 1회 SELECT → 메모리 dict 로드
         {file_path: (hash, size, mtime, os_doc_id)}
단계 3: 파일별 판단
  ┌─ 로컬에 없음                    → 신규 → read_bytes → 색인
  ├─ 로컬 있음 + size&mtime 동일    → SKIP (read_bytes 호출 X)
  └─ 로컬 있음 + size/mtime 다름    → read_bytes → 해시 비교
                                       ├─ 해시 다름: 재색인
                                       └─ 해시 동일: mtime만 갱신
```

### 5.4 체크포인트 기반 재개

- `SyncJob.cursor_value`에 **마지막 처리 파일 경로** 저장
- walk 순서는 사전식 정렬 보장 필요 (SMBClient/SFTPClient.walk 구현 시 정렬 추가)
- 재개 시 walk 시작부터 `cursor_value`까지 빠르게 스킵 → 이후부터 실제 처리

### 5.5 배치 UPSERT

파일마다 개별 INSERT/UPDATE 대신 chunk(예: 300건) 단위로:

- PostgreSQL: `INSERT ... ON CONFLICT DO UPDATE`
- MySQL: `INSERT ... ON DUPLICATE KEY UPDATE`
- SQLite: `INSERT ... ON CONFLICT DO UPDATE`

### 5.6 세션 안정성

- TCP keepalive: SMBClient 생성 시 socket 옵션
- 배치 사이 주기적 세션 헬스 체크 (1분마다 list_dir)
- 끊김 시 1회 자동 재연결 (기존 로직 유지)
- 재연결 실패 시 Job 실패 처리 → 다음 polling에서 다른 워커가 체크포인트부터 이어받음

### 5.7 병렬도 제한

- SMB 서버 부하 보호를 위해 소스당 동시 1 Job만 허용
- Job claim SQL에 `AND NOT EXISTS (... same source running)` 조건 추가

### 5.8 10만 파일 기준 부하 비교

| 지표 | 현재 | 개선 후 |
|---|---|---|
| 네트워크 read_bytes | 10만 파일 | 변경/신규만 |
| SMB 세션 | 실행당 1회 | 동일 |
| 로컬 DB 상태조회 | 10만 쿼리 | 1회 bulk SELECT |

| 장애 복구 | walk 처음부터 | 마지막 처리 파일부터 |

## 6. 두 설계의 공통점과 차이점

| 항목 | DB 색인 | SMB/SSH 색인 |
|---|---|---|
| 증분 판별 | cursor_column 값 비교 | size + mtime → 필요시 해시 비교 |
| 원천 접근 최소화 | LIMIT + WHERE로 신규만 SELECT | walk 메타만, read_bytes는 변경 후보만 |
| 체크포인트 단위 | 마지막 PK 값 | 마지막 처리 파일 경로 |
| 커넥션 재활용 | 엔진 캐시 (프로세스 전역) | SMB 세션 (Job 단위) |
| Upsert 키 | `{source.name}:{pk}` | `os_doc_id` (FileIndexState 저장값) |
| 임베딩 배치 | 공통 `index_bulk` | 공통 `index_bulk` |
| OpenSearch 벌크 | 공통 `index_bulk` | 공통 `index_bulk` |
| 워커 큐 | 공통 `SyncJob` | 공통 `SyncJob` |
| 병렬도 | 소스당 1 Job | 소스당 1 Job |

## 9. 운영상 주의사항

1. **삭제 감지 없음**: 원본 삭제분은 검색 결과에 계속 노출됨 → 필요 시 "전체 재색인" 버튼으로 수동 대응. 반기/연 1회 권장.
2. **초기 전체 색인 부담**: 첫 실행 시 cursor 값이 비어 있어 전수 처리 필요 → 야간 실행 권장, 중단 시 체크포인트로 이어감.
3. **cursor_column 인덱스**: 외부 DB에 인덱스 없으면 풀스캔 발생 → 관리자에게 사전 고지.
4. **Materialized View 사용 시**: MV 새로고침 주기 ≥ 색인 주기로 설정 필요.
5. **뷰(View) 기반 소스**: PK/updated_at/tombstone 보장이 없으면 증분이 부정확할 수 있음 → 뷰 제공자와 협의 필요.
