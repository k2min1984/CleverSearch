# CleverSearch 검색 화면 4개 신고 수정 기록

- 작업일: 2026-09-30
- 대상: CleverSearch 사용자 검색 화면(8000번)
- 신고 번호: CS-12 / CS-24 / CS-26 / CS-40
- 백업: `source-backups/search-ui-20260930-131450`

## 1. CS-12 문서 제목 클릭 후 빈 새 창

### 확인과 수정

- 기존 방식은 `about:blank` 새 창을 열고 원래 검색 페이지가 그 창에 `document.write()`로 내용을 써 넣는 구조였다.
- 사용자 환경에서 빈 창 신고. 도구로 기존 제목을 클릭했을 때도 사용할 수 있는 읽기 탭이 생성되지 않았음. 브라우저 콘솔에 구체적 예외는 없었으므로 CSP 오류 등 특정 브라우저 내부 원인까지 단정하지 않음.
- 실제 주소를 갖는 읽기 페이지 `/static/user/document.html?id=...&q=...`를 추가했다. 제목을 실제 새 탭 링크로 바꾸고 카드 클릭도 같은 주소를 연다.
- 읽기 페이지가 직접 본문 API를 호출하므로 새로고침·주소 재접속이 가능하다. 로딩·실패·재시도 안내를 제공한다.
- 본문은 텍스트 노드로 삽입하고 강조할 부분만 mark 요소로 만든다. 본문에 포함된 HTML을 실행하거나 `<mark>` 글자를 그대로 노출하지 않도록 처리했다.

### 검증

- 실제 브라우저에서 `1. 연구개발계획서 양식_울산지방청.pdf` 제목 클릭 → 새 탭 생성 → 제목·파일 정보·한글 본문 표시 확인.
- 본문 15,165자, 강조 요소 2개, 문자 그대로의 `<mark>` 없음, 읽기 탭 콘솔 오류 없음 확인.
- 새로고침 후에도 접근성 화면에서 본문 표시 확인. 직후 DOM 검사 도구는 선택자 시간 초과가 발생했지만 실제 페이지 본문은 접근성 화면에 정상 표시되어 도구 문제와 앱 상태를 구분했다.
- 검증한 PDF 읽기 탭은 결과 확인용으로 남겼다.

## 2. CS-24 최근 검색어 삭제 시 검색까지 실행됨

### 원인과 수정

- 검색어 행 안에 삭제 버튼이 있다. 행의 클릭 처리가 바깥 목록의 삭제 처리보다 먼저 실행되어 검색어 선택/검색이 발생했다.
- 검색어 행의 클릭 처리에서 안쪽 버튼 클릭을 제외했다. 키보드 Enter/Space도 행 자체가 대상일 때만 선택하도록 보완했다.
- 삭제 API가 끝나면 목록을 다시 읽고 완료 안내만 표시한다.

### 검증

- 기존 사용자 검색어를 지우지 않도록 `CS삭제클릭검증20260930`을 시험용으로 검색해 최근 목록에 추가.
- 연구개발계획서 결과를 띄우고 검색창을 비워 최근 검색어 목록을 연 뒤, 시험용 검색어의 삭제 버튼 클릭.
- 해당 행이 즉시 사라짐. 삭제 전후 검색창 값·주소·검색 결과 내용이 모두 동일함을 비교해 확인.
- 목록을 닫았다 다시 열어도 삭제한 행은 0건. 나머지 최근 항목은 유지.
- 전체 삭제는 실행하지 않음. 검증 검색 자체의 검색 로그는 남음.

## 3. CS-26 운영지침 검색에 무관한 PDF가 나옴

### 본문 확인

- 해당 PDF의 색인된 본문 15,165자에서 `운영지침`은 0회였다. 공백·줄바꿈을 제거한 뒤에도 해당 문자열이 없었다.
- `운영요령`, `연구실운영비`, `이 지침`처럼 운영/지침이 각각 존재했다.
- 실제 OpenSearch 분석 결과 `운영지침`은 `운영`, `지침` 두 토큰으로 나뉘었다.
- 기존 AND 검색은 두 토큰이 문서 어딘가에 각각 있으면 통과시켰다. 문서에 운영지침이라는 표현이 없는데도 나온 원인이었다.

### 수정

- 띄어쓰기 없는 단일 검색어는 제목/본문에서 분석된 단어들이 순서대로 인접해야 하는 `match_phrase` 계열 조건을 추가했다.
- 조건을 검색 엔진에 보내는 단계에 적용해 결과 건수·분류 집계·페이지 이동도 같은 조건을 사용한다.
- 여러 단어로 입력한 검색, 동의어 확장 경로와 초성 검색 경로는 유지한다.
- 한국어 분석기 기준의 구문 일치 조건이다. 모든 검색을 원문 문자 단위 완전 일치로 바꿨다는 의미는 아니다.

### 검증

- 수정 전 운영지침 검색 3건 → 수정 후 2건. 신고한 PDF 제외 확인.
- 남은 문서: `2026_운영지침_보안.pdf.jpg`(제목에 포함), `통합검색솔루션_종합문서_20260123_V001.xlsx`(본문에 포함).
- 연구개발계획서 검색은 3건이며 해당 PDF가 계속 포함된다.
- 초성 `ㅇㄱㄱㅂㄱㅎㅅ`, 오타 `연구개발계휙서` 검색에서 기대 문서 유지. 없는 검색어는 0건.
- 운영지침을 페이지당 1건씩 조회해 총 2건 유지, 1·2페이지 중복 없음 확인.
- 실제 두 브라우저 탭에서 연구개발계획서 3건 / 운영지침 2건이 각각 유지되고, 확인한 두 검색 탭의 콘솔 오류 0건.

## 4. CS-40 인기 검색어 5개 설정인데 4개 표시

### 원인과 수정

- 관리자 저장값은 기간 7일/표시 5개였고 사용자 인기 검색어 API도 이미 5개를 반환했다.
- 사용자 검색창 추천 목록이 응답을 다시 `.slice(0, 4)`로 잘랐고, 최근/개인 추천에 있는 단어까지 빼서 개수가 더 줄 수 있었다.
- 인기 검색어 영역은 API에서 관리자 설정에 맞춰 받은 목록 전체를 표시하도록 수정했다. 서로 다른 영역 사이의 중복 때문에 인기 검색어 수를 줄이지 않는다.

### 검증

- 현재 설정 `{days:7, limit:5}` 유지.
- API 반환 5개, 사용자 상단 인기 검색어 5개, 검색창을 눌러 펼친 인기 검색어도 5개 확인.
- 집계된 고유 검색어가 설정값보다 적으면 실제 있는 개수까지만 나오는 것이 정상이다.
- 추가 관리자 화면 확인용 탭은 세션 만료로 로그인 화면이 나와 닫았다. 설정 재저장/변경 시험으로 기록하지 않으며, 이미 저장된 설정·API·사용자 표시를 대조해 검증했다.

## 실행·검증 기록

- 프로젝트의 기존 미커밋 변경을 유지하고 위 파일만 이번 작업에서 변경. 기존 파일은 작업 직전 백업.
- JS 구문 검사(검색 화면 2개, 읽기 HTML/JS), Python 구문 검사 통과.
- 기존 초성·확장자·날짜 필터 회귀 검사 `tests/test_search_chosung_mode.py`: 격리된 테스트 설정에서 **6 passed**.
- 실제 HTTP 검사 **10개 확인 통과**: 주요 검색 5종, 페이지 분리, 인기 개수, 화면/JS 응답 등. 전체 시나리오를 10개로 대체해 통과 처리한 것은 아님.
- Search 서버만 1회 재시작. 새 launcher PID 2760. Chat 서버 재시작 없음.
- 전후 상태: 스케줄러 중지, 파일 감시 중지, 네트워크 감시 실행/30초, 기존 색인 작업 1·2·3 완료 유지. 재시작에 따라 메모리의 스케줄러 마지막 확인 시각은 초기화됨.
- 원본 문서/색인 삭제·재색인·DB 초기화 없음. 최근 검색어 삭제는 새로 만든 시험 항목 한 건만 실행.
- 사용자용 시험 결과표는 덮어쓰지 않고 시나리오 설명만 보완.
- 작업 도구 중 빈 문자열 fill이 입력을 비우지 않아 실제 Ctrl+A/Backspace로 진행했고, 읽기 새로고침 후 DOM 검사 시간 초과는 접근성 화면으로 확인. 앱 오류와 혼동하지 않음.
- 초기 상태 확인에 이전 `25-scheduler-state.py before`를 사용해 `scheduler-before.json`이 이번 확인 시점으로 갱신됨. 이번 작업의 독립 전후 증거는 아래 `search-ui-runtime-before/after.json`에 저장했다.
