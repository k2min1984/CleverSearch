## 1. 작업 배경

### 1.1 기존 흐름의 한계

[외부에이전트_파일감지_20260428_현승준.md](외부에이전트_파일감지_20260428_현승준.md) 의 1차 구조에서 다음 한계가 확인됨:

| # | 한계 | 영향 |
|---|---|---|
| 1 | 다른 PC가 이미 색인한 파일을 새 PC가 풀업로드 | 네트워크 비용 + 서버 SHA 계산까지 도달 후 중복 컷 |
| 2 | `registered_files.txt` 초기화·재설치 후 폴더 전체 재전송 | 실제 신규 파일이 0% 여도 풀스캔 분량 만큼 트래픽 발생 |
| 3 | 전송 무결성 검증 부재 | 네트워크 손상/잘림 발생해도 잘못된 본문이 그대로 색인 진입 |
| 4 | 로그·이력에 SHA 추적 단서 없음 | "이 파일이 어디서 들어왔는가" 디버깅 곤란 |
| 5 | 에이전트 측 1차 차단 키가 64KB sha1 — 앞부분만 같은 파일은 이론상 충돌 가능 | 드물지만 잘못된 스킵 가능성 |

### 1.2 본 작업의 목표

세 가지를 동시에 달성한다:

1. **전송량 절감** — 서버에 이미 있는 파일은 본문 업로드 자체를 안 하도록 사전 질의 도입
2. **무결성 보장** — 클라이언트 SHA 와 서버 재계산 SHA 를 비교해서 전송 중 손상 차단
3. **디버깅 추적성** — 모든 단계(에이전트 응답 / 서버 로그 / IndexingHistory / DB) 가 동일한 SHA-256 으로 grep 가능

## 3. 새 프로세스 흐름 (전체)

### 3.1 단일 파일 처리 흐름 (3단 방어선)

```
[에이전트 PC]
  watchdog 감지 → 안정화 대기
    ↓
  ┌─ 1단(로컬 registry): 경로|크기|mtime|앞64KB sha1 ─────────────┐
  │  └ 적중 시 종료 (네트워크/SHA 계산 비용 0)                    │
  │                                                                │
  ↓ 미적중                                                          
  전체 SHA-256 계산 (1MB 청크 스트리밍)                              
    ↓                                                                
  ┌─ 2단(서버 사전 질의): GET /agent-check?sha256=... ───────────┐
  │  └ exists=true → 로컬 registry 에 추가 + 종료 (본문 전송 0)    │
  │                                                                │
  ↓ exists=false 또는 네트워크 장애(폴백)                           
  POST /agent-notify  ← 헤더: X-Agent-Key, X-File-SHA256, X-File-Size
    ↓                                                                
─────────────────────────────────────────────────────────────────
[서버]                                                               
  ① 인증 (_verify_agent_key)                                         
  ② 헤더 SHA / Size 형식 검증 (400)                                   
  ③ Size 가 100MB 초과 - 본문 받기 전 차단 (413)                      
  ④ ┌─ 3단(서버 헤더 SHA DB 조회): claimed_sha 가 DB 에 있나? ────┐
     │  └ 있음: 본문 받지 않고 즉시 skipped 반환 (전송 비용 거의 0) │
     │                                                                │
  ⑤ 본문 수신 (UploadFile.read)                                       
  ⑥ 서버 재계산 SHA-256 = actual_sha                                  
  ⑦ 무결성 검증: claimed_sha != actual_sha → 422                      
  ⑧ 크기 검증:   claimed_size != len(content) → 422                    
  ⑨ DB 중복 컷 (actual_sha) — 헤더 누락 케이스도 보호                 
  ⑩ IndexingService.index_bytes() → 파싱 → 임베딩 → OpenSearch        
  ⑪ IndexingHistory 누적 (last_sha 포함)                              
```

### 3.2 다단 방어선의 의미

| 방어선 | 키 | 시야 | 차단 시점 | 절감 비용 |
|---|---|---|---|---|
| 1단 (에이전트 registry) | 경로\|크기\|mtime\|앞64KB sha1 | 이 PC 만 | 네트워크 호출 전 | 네트워크 + SHA 계산 + 서버 모든 처리 |
| 2단 (서버 /agent-check) | 전체 SHA-256 | 서버 전역 | 본문 전송 전 | 본문 전송 + 서버 본문 수신 + 파싱 + 임베딩 |
| 3단 (서버 /agent-notify 헤더 SHA) | 전체 SHA-256 (claimed) | 서버 전역 | 본문 수신 전 | 본문 수신 후처리 + 파싱 + 임베딩 |
| 4단 (서버 /agent-notify 본문 SHA) | 전체 SHA-256 (actual) | 서버 전역 | 색인 직전 | 파싱 + 임베딩 + OpenSearch |

→ **2단·3단이 신규**. 4단은 기존 보호 그대로 유지(헤더 누락 클라이언트, 헤더 검증 우회 시도 모두 차단).

### 3.3 무결성 검증 흐름

```
[에이전트]
  calc_sha256(file)  →  claimed_sha
  POST + X-File-SHA256: claimed_sha
                          ↓
[서버] await file.read() → content
       hashlib.sha256(content).hexdigest() → actual_sha
       
       claimed_sha == actual_sha ?
         ├── 같음 : 정상 진행 (DB 중복 컷 → 색인)
         └── 다름 : 422 + 로그 경고 + IndexingHistory 에 fail 기록
                   (네트워크 손상 / 의도적 위변조 시도 차단)
```

### 3.4 사전 질의 응답 형식

```http
GET /api/v1/index/agent-check?sha256=<64자 16진수>
Header: X-Agent-Key: <키>

200 응답 (적중):
  { "exists": true, "sha256": "...", "doc_id": 123, "origin_file": "회의록.pdf" }

400: sha256 형식 오류
401: 유효하지 않은 키
503: AGENT_API_KEY 미설정
```

## 4. 기능 적용 이유 (왜 이 구조인가)

### 4.1 왜 사전 질의 + 본문 헤더 SHA 둘 다 두는가

- **사전 질의(2단)**: GET 1회로 본문 전송 결정. 빠르고 쌈. 그러나 **에이전트가 보낸 SHA 와 실제 본문이 다를 수 있다는 위험**(악의적/버그) 이 남음
- **본문 헤더 SHA(3단)**: POST 진입 시점 헤더만으로 한 번 더 컷. 본문 SHA 와 비교하면서 무결성도 검증
- **본문 SHA(4단)**: 헤더 누락 클라이언트(레거시/타 도구)도 보호하기 위해 기존 컷 유지
- **결론**: 세 단계가 서로 다른 공격면/오류면을 막음 → 어느 하나만 두면 빈 구멍 발생

### 4.2 왜 서버에서 SHA 를 항상 재계산하는가

- 클라이언트가 보낸 sha 를 신뢰만 하면, 다른 본문을 끼워 넣어 색인 우회 가능 (보안)
- 네트워크 손상으로 일부 바이트 변경 시 본문은 정상처럼 보이고 sha 만 어긋남 (정합성)
- 1GB 당 약 1~2초 CPU 비용은 파싱+임베딩 회피 이득에 비하면 매우 작음

### 4.3 왜 헤더가 아닌 multipart form 필드로 안 보내는가

- multipart 는 **본문 파싱이 끝나야** 필드 값을 얻을 수 있음 → 본문 받기 전 컷이 불가능
- 헤더는 HTTP 첫 라인 직후 즉시 읽힘 → "본문 받기 전 차단" 의 핵심 전제
- 따라서 SHA / Size 는 반드시 **헤더**로 전달

### 4.4 왜 사전 질의가 실패해도 본문 업로드로 폴백하는가

- 네트워크 일시 장애로 사전 질의가 실패해도 색인 자체는 시도되어야 함 (가용성 우선)
- 폴백 시에도 4단 본문 SHA 검증이 있으므로 정합성은 보장
- `check_exists` 가 `{"unknown": true}` 를 반환하는 모든 케이스에서 자연스럽게 본문 업로드 진행

### 4.5 왜 64KB sha1 로컬 키를 그대로 두는가 (전체 sha256 으로 갈아엎지 않음)

- 1단 차단의 목적은 **자기 PC 의 빠른 컷** — 큰 파일도 64KB 만 읽으면 충분히 식별 가능
- 전체 sha256 으로 바꾸면 폴더 전체 스캔 시 PC 디스크 read I/O 가 폭증 (→ 의도된 1단 효과 손상)
- 1단을 통과한 경우에만 전체 sha256 을 계산 (네트워크 보낼 가치가 있는 시점에만 비용 지불)

### 4.6 왜 last_sha 를 IndexingHistory message JSON 에 넣는가 (별도 컬럼이 아닌)

- 이력 폭증 방지를 위해 일자별·IP별 1행 누적 정책 유지 → 컬럼 추가 시 마이그레이션 필요
- "마지막으로 처리된 파일의 SHA" 라는 디버깅 단서로는 message JSON 안에 넣어도 충분
- 추후 PR 에서 검색·인덱싱 빈도 따라 컬럼화 검토 가능

### 4.7 왜 422(Unprocessable Entity) 인가 (400/500 아님)

- 400 (Bad Request): 형식 오류 — 헤더 형식 자체가 깨졌을 때 사용
- 422 (Unprocessable): 형식은 맞지만 의미가 안 맞을 때 — claimed_sha vs actual_sha 불일치, size 불일치
- 500: 서버 측 버그 — 무결성 위반은 클라이언트의 입력 문제이므로 4xx

### 4.8 왜 에이전트 GUI 로그에 `[OK/precheck]` 태그를 분리했는가

- 사전 질의 적중과 풀업로드 후 색인 성공의 비율을 운영자가 즉시 구분 가능
- 사전 질의 적중률이 높다 = 다PC 간 중복이 많거나 재스캔이 잦음을 의미 → 운영 패턴 진단 단서
- 부하 분석 시 "정말 필요한 색인 비율" 을 한눈에 파악

## 5. 영향 범위 및 호환성

### 5.1 기존 클라이언트 호환

- **헤더 누락 클라이언트**도 그대로 동작 — 헤더 검증은 "있을 때만" 수행
- 기존 `registered_files.txt` 형식 무변경 → 기존 사용자가 에이전트 업데이트 후에도 등록 기록 유지
- 이번 변경으로 인한 DB 스키마/마이그레이션 없음

### 5.2 영향 받는 곳

| 영역 | 영향 |
|---|---|
| 검색 / 사용자 업로드 | 영향 없음 (라우트/로직 변경 없음) |
| SMB/SSH/DB 색인 경로 | 영향 없음 |
| 관리자 대시보드 | `agent_summary` JSON 에 last_sha 가 추가되지만 기존 키도 유지 → 화면 표시 코드 무변경 |
| 외부 에이전트 (구버전 exe) | 헤더 미동봉 시에도 동작. 단 사전 질의/무결성 검증 효과는 누락 |
| 외부 에이전트 (신버전 exe) | 사전 질의 + 헤더 모두 활용 |

### 5.3 점진적 롤아웃

1. **서버만 먼저 배포** — 헤더가 없어도 기존 동작 유지되므로 안전
2. **에이전트 exe 빌드/배포** — 사용자가 신버전을 받으면 그 PC 부터 사전 질의/헤더 SHA 활용 시작
3. **운영 모니터링** — `[OK/precheck]` 비율로 사전 질의 효과 측정

## 7. 후속 작업 (Roadmap)

이번 PR 은 "전송 절감 + 무결성 + 추적성" 의 1단계. 어제 합의된 큰 그림에서 남은 것:

| 우선순위 | 항목 | 상태 |
|---|---|---|
| 1 | SHA 사전 질의 + 무결성 검증 + 디버깅 강화 | **본 PR (완료)** |
| 2 | SyncJob 큐로 색인 비동기화 (`source_type='agent'`) — 다른 기능 보호 | 미진행 |
| 3 | 임시파일 inbox + 디스크 백프레셔 (429 + Retry-After) — 1TB↔500GB 비대칭 대응 | 미진행 |
| 4 | 워커 동시성 환경변수화 (`AGENT_INDEX_CONCURRENCY`) | 미진행 |
| 5 | 에이전트 측 5xx 지수 백오프 + Retry-After 존중 | 미진행 |
| 6 | 임베딩 캐시 (SHA → 벡터) | 검토 단계 |

**다음 PR 후보**: 2 + 3 + 4 를 한 묶음(SyncJob 비동기 색인 + 백프레셔)으로 진행하면 부하 격리·디스크 보호가 동시에 마무리됨.

## 8. 빠른 시작 (운영자용)

### 8.1 서버 배포

기존 `.env` 의 `AGENT_API_KEY` 를 그대로 사용. 추가 설정 필요 없음.

### 8.2 에이전트 빌드 (PC 측 신버전 exe)

```bash
cd agent
build.bat
# → agent/dist/CleverSearchAgent.exe  (구버전 대체)
```

신버전 exe 는 자동으로 사전 질의를 시도. 서버가 구버전(404)이면 폴백으로 풀업로드.

### 8.3 효과 확인

- 관리자 화면 → 색인 이력 → `agent_summary` 행의 `last_sha` 표시
- 에이전트 GUI 로그에서 `[OK/precheck]` 태그 비율 확인
- 폴더 전체 재스캔 시 네트워크 트래픽 감소 측정 (이전 대비)

### 8.4 사전 질의 수동 테스트

```bash
# 적중 케이스
curl -k -H "X-Agent-Key: <키>" \
  "https://<서버>/api/v1/index/agent-check?sha256=<DB에 있는 sha>"
# → {"exists":true,"sha256":"...","doc_id":...,"origin_file":"..."}

# 미적중 케이스
curl -k -H "X-Agent-Key: <키>" \
  "https://<서버>/api/v1/index/agent-check?sha256=0000...0000"
# → {"exists":false,"sha256":"..."}
```

## 9. 트러블슈팅

| 증상 | 원인 / 조치 |
|---|---|
| 로그에 `[OK/precheck]` 가 안 나옴 | (a) 신버전 에이전트 미적용 (b) 서버가 구버전(404) → 둘 중 하나 업그레이드 필요 |
| 422 "전송 무결성 오류" 다수 발생 | 네트워크 불안정 / 안티바이러스가 본문 변조 / 클라이언트 SHA 계산 버그 → 에이전트 로그의 `sha256` 필드와 서버 로그 `claimed=... actual=...` 비교 |
| 422 "전송 크기 불일치" | 위와 동일 — 거의 같은 시나리오 |
| 사전 질의가 항상 미적중 | DB 의 `IndexedDocument.content_hash` 가 비어있거나 다른 알고리즘 → DBService.find_duplicate_by_content_hash 점검 |
| 400 "X-File-SHA256 형식 오류" | 클라이언트가 대문자 SHA 또는 길이가 다른 값 전송 → `[0-9a-f]{64}` 만 허용 |
| 사전 질의에서 401 | API Key 가 다름 → 본문 업로드도 어차피 401 이므로 GUI 메시지로 알림 |
