# CleverSearch CS-50 동기화 대기 및 결과 표시 오류 수정

## 사용자에게 보인 문제

사용자가 제공한 2026-09-30 11:46 캡처에서 접수번호 1번의 상태는 `pending`, 타입은 `undefined`였다. 버튼 순서는 맞았다. 처음 안내했던 것처럼 기다리기만 하면 끝나는 상황이 아니었으며, 실제 처리를 맡는 기능이 꺼져 있었다.

## 원인과 수정

| 문제 | 확인한 원인 | 수정 |
|---|---|---|
| 동기화가 계속 대기 | 앞선 로컬 설정 작업에서 `.env.workstation`의 `AUTO_START_INDEX_WORKER=false`로 저장됨. 실행 로그에도 워커 비활성화 표시 | 실제 실행 설정을 `true`로 수정하고 CleverSearch 재시작. 재준비 스크립트도 수정. 자동 테스트 환경은 격리를 위해 `false` 유지 |
| 재접수 알림에 `undefined` | 진행 중 작업을 재사용하는 응답에 `source_type`과 `mode`가 없었음 | SMB/SSH/로컬 및 DB 중복 응답에 실제 기존 작업의 타입과 모드를 포함. DB 신규 응답에도 타입 포함 |
| 접수를 완료처럼 읽기 쉬움 | 알림에 “등록 완료”와 기술 용어 표시 | “동기화 작업이 접수되었습니다” 또는 “이미 접수된 작업”으로 구분하고 로컬 폴더·대기 등 쉬운 말과 완료 확인 위치 표시 |
| 아래쪽 통합 이력이 비어 있음 | 폴더 작업 처리기가 카드 이력인 SmbSyncHistory만 기록하고 통합 이력인 IndexingHistory에는 기록하지 않음 | 로컬/SMB/SSH 폴더 작업의 두 이력을 같은 트랜잭션에 저장. 실패/부분 성공 구분, 로컬·SSH·부분 성공 필터 보완 |
| 변경 없는 파일의 처리 건수가 빠짐 | 본문을 다시 색인한 파일만 작업 카운터에 반영하고 메타/해시 일치로 건너뛴 파일을 누락 | 완료 시 기존 체크포인트 건수에 이번 처리 결과를 합산. 변경 없는 파일을 처리/건너뜀에 포함하고 마지막 파일 위치 보존 |

원본 소스 백업: `source-backups/sync-job-20260930-115205`. 비밀값을 백업 기록에 출력하지 않고 변경한 워커 설정 한 항목만 기록했다.

## 실제 확인 결과

### 사용자가 접수한 1번 작업

- 수정 전: pending, 처리 0건, 시작/종료 시간 없음.
- 첫 번째 서버 재시작 후: **done, 처리 1건, 색인 1건, 스킵 0건, 실패 0건**.
- 브라우저 통합 색인 이력의 위쪽 작업 목록에서도 같은 결과를 확인.
- 1번은 통합 이력 기록 수정 전 완료됐으므로 아래쪽 통합 요약이 소급 생성되지는 않았다. 기존 작업 행과 카드 이력은 보존했다.

### 수정 후 재검증한 2번 작업

- 같은 시험용 로컬 폴더에 실제 HTTP API로 증분 동기화 1회 요청.
- 접수 응답에 `source_type=local`, `mode=incremental`, `job_id=2` 포함.
- **done, 처리 1건, 색인 0건, 스킵 1건, 실패 0건**. 변경 없는 문서를 다시 처리하지 않는 정상 결과.
- 아래쪽 통합 이력에 `success`, `총 1건 (성공 0 / 실패 0 / 스킵 0 / 변경없음 1)` 기록.
- 위쪽 스킵 1은 변경 없음도 합친 값이고, 아래쪽 요약은 스킵과 변경 없음을 나누어 보여준다.
- 문서 총 건수는 수정 전후 **6건**. 자료 삭제·전체 초기화 없음.
- Search 검색 페이지와 Chat 상담 페이지 모두 HTTP 200 확인.

### 자동 검사

- `tests/test_sync_job_enqueue_contract.py`: 로컬/SMB/SSH/DB × 대기/실행/일시정지 12개 검사.
- `tests/test_sync_job_history.py`: 이력 조회 5개 및 변경 없는 파일의 처리/재개 건수 1개 검사.
- **합계 18개 통과**. SQLite 메모리 DB를 사용하며 실제 사용자 DB를 삭제하지 않음.
- SMB/통합 이력 화면 JavaScript 및 준비 스크립트 PowerShell 구문 검사 통과.
- 증거: `sync-job-before.json`, `sync-job-after.json`, `sync-job-http-verification.json`, `sync-job-regression-tests.xml`.

## 실행 중 이슈와 범위

- 제한 환경에서 프로젝트 Python 프로세스 생성과 Windows 프로세스 조회가 차단되어 자동 승인 검토를 거쳐 실행.
- 서버 재시작은 기존 Search 실행 스크립트와 자식 프로세스, 8000 포트 소유자를 확인한 뒤 진행. Chat 프로세스는 재시작하지 않음.
- 두 번째 재시작 중 관리자 탭이 연결 오류 페이지에 머물렀다. 서버 준비 후 새 탭은 정상 열렸으나 브라우저 도구의 확인창 조작이 시간 초과되어 재실행은 실제 HTTP API로 검증. 해당 UI 확인창의 전체 재검증까지 완료했다고 표현하지 않음.
- 사용자 수동 결과표를 임의로 통과 처리하지 않음. 이번 작업은 CS-50/51 관련 수정과 검증이며 전체 158개 수동 시험 완료가 아님.
- 외부 SMB/SSH 서버와 회사 DB에 접속해 검증한 결과가 아니다. 현재 로컬 폴더 작업 완료 및 응답/이력 계약에 대한 결과이다.

## 최종 브라우저 확인

- 확인창 제어가 지연된 검증 탭을 닫고 정상 주소로 결과 탭을 새로 열어 복구했다.
- 2026-09-30 12:03:47 최종 실제 화면에서 작업1·2·3 모두 done, 실패0 확인. 2·3은 처리1/색인0/스킵1로 표시.
- 브라우저 확인 중 추가 접수된 3번도 정상 완료됐으며, 아래쪽 통합 이력에는 재검증 회차 두 건 모두 성공/변경없음1로 표시됐다. 3번의 접수 조작 시점은 도구 시간 초과가 있어 단정하지 않는다.
- 로컬 폴더·SSH/SFTP·부분 성공 필터가 실제 화면에 나타났고 완료 결과 탭을 사용자에게 열어 두었다. 새 알림창 자체의 캡처까지 확보한 것은 아니다.
