# 신규 Word 시험 파일 깨짐 신고 점검 및 수정

## 대상과 현재 판단

- 프로젝트: CleverSearch의 CS-27 신규 업로드 및 CS-31 중복 검사 자료.
- 사용자 신고: 파일 안의 내용이 깨져 보임. Word 화면인지, 코드 편집기인지, 웹 미리보기인지 확인 질문을 보냈으나 아직 답을 받지 못함.
- 기존 파일의 ZIP 검사 및 한글 네 문장 추출은 정상. 한글 자체가 잘못 저장된 증거는 없음.
- 별도로 실제 구조 결함 확인: 기존 생성기가 XML을 다시 저장하면서 `w14`, `wp14` 네임스페이스 선언을 없앴으나 `mc:Ignorable="w14 wp14"` 참조는 남겼음. Word 호환성 문제를 일으킬 수 있어 수정. 사용자 화면의 직접 원인이라고 단정하지 않음.
- 이전 자료 준비 때 텍스트 추출만 확인했고 실제 Word 페이지를 눈으로 확인하지 못한 검증 누락이 있었음.

## 수정

- 기존 두 파일은 `source-backups/docx-repair-20260930-104828`에 보존.
- `수동검증_신규문서_20261001.docx`를 python-docx로 다시 작성하고 한글 글꼴을 맑은 고딕으로 지정. 제목과 기존 한글 네 문장 및 검색어를 유지.
- 같은 파일을 `수동검증_이름만변경_20261001.docx`로 복사해 CS-31의 동일 내용 조건 유지.
- 재발 방지를 위해 `17-prepare-manual-test-data.py`의 XML 직접 치환을 `manual_test_docx.py` 호출로 변경. 전체 자료 준비 스크립트를 재실행하지 않고 DOCX 두 개만 갱신.
- `신규업로드문서_내용확인.md`에 사람이 바로 읽을 본문과 Word로 여는 방법을 제공.

## 검증한 것과 아직 확인하지 못한 것

- ZIP 손상 없음, 한글 네 문장 완전 일치, 선언 없는 Ignorable 네임스페이스 참조 0개.
- 두 DOCX의 바이트 및 SHA-256 일치.
- CleverSearch 실제 `app/core/file/office.py`의 `parse_word()`를 호출하여 페이지 표시와 네 문장이 정확히 추출되는지 확인. 서버 업로드 시험과는 별개임.
- 증거: `docx-repair-qa/verification.json`.
- 문서 스킬이 요구하는 `render_docx.py` 실행은 `LibreOffice soffice.exe was not found on PATH`로 실패. 제공된 Windows 의존성에도 LibreOffice가 없음. 연결된 Word 문서 세션도 없음. 따라서 실제 페이지 렌더링 및 Word 화면 정상 여부는 **미검증**이며 시각 검증 완료로 표시하지 않음.
- 현재 브라우저의 관리자 업로드 안내는 정상 한글로 표시되며 업로드 대기 영역을 확인. 사용자가 봤던 깨진 화면은 확보하지 못함.

## 시험할 때 주의할 점

- DOCX를 코드 편집기로 열면 압축 파일의 `PK` 등 기호가 보일 수 있음. 그런 화면이라면 탐색기에서 **연결 프로그램 → Word**로 열어 확인하거나 내용 확인 MD를 읽음.
- 웹 업로드에는 DOCX를 선택. MD는 사람이 내용을 읽기 위한 별도 안내임.
- 파일을 다시 만들었으므로 이전 버전과 파일 해시가 달라짐. 이전 버전을 이미 등록했다면 새 버전 업로드가 중복으로 차단된다고 가정하면 안 됨. CS-27 시작 전 문서 목록과 기준 건수를 다시 확인하고 신규 시험 조건을 정리해야 함.
- 이번 점검에서는 파일을 업로드하거나 기존 DB 자료를 삭제하지 않았으며 사용자 결과표도 변경하지 않음.

## 승인 및 변경 범위

- 사용자 오류 신고와 기존 로컬 수정 위임 범위에서 중앙 작업 폴더의 테스트 자료와 생성기 및 MD를 수정.
- 위 작업은 허용된 작업 폴더에서 일반 실행으로 완료. 사용자가 별도 승인 버튼을 눌렀다고 기록하지 않음.
- 프로젝트 docs 사본 쓰기는 별도의 도구 자동 승인 검토 결과를 승인내역 A-023에 기록.
