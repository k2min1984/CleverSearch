## 1. 백엔드 인프라 보강

### B-1. 비밀번호 만료 강제 흐름
**왜**: M-3 에서 정책·변경 API 만 도입. `AUTH_PW_MAX_AGE_DAYS=90` 환경변수는 정의돼 있으나 실제 검사·강제 로직은 미적용 상태.

**할 일**
- [app/core/security.py:authenticate_user](../app/core/security.py) 성공 분기에서:
  ```python
  age_days = (now - user.last_password_changed_at).days if user.last_password_changed_at else None
  if settings.AUTH_PW_MAX_AGE_DAYS and age_days and age_days >= settings.AUTH_PW_MAX_AGE_DAYS:
      user.must_change_password = True
  ```
- 시드 계정에는 last_password_changed_at = NULL → "변경한 적 없음 = 강제 변경"으로 동작 (기존 must_change_password=True 와 정합)
- 변경 시점에 `last_password_changed_at = now()` 갱신 (이미 `change_password` 에 적용됨)

**관련 표준**: 국정원 「소프트웨어 개발보안 가이드」 인증 — 주기적 비밀번호 변경.

**예상 작업량**: 0.5일.

---

### B-2. 관리자 행위(admin action) 추가 audit 기록
**왜**: M-5 에서 `audit_logs` 테이블 + 인증 관련(login/MFA/password_change) 만 기록. 사용자 추가/삭제/권한 변경/인덱스 삭제/카드 등록 등 운영자 액션은 미기록.

**할 일** — 기록 지점 추가:
| 액션 | 위치 |
|---|---|
| `user_create` / `user_delete` / `user_disable` | (사용자 관리 API 신설 필요) |
| `role_grant` / `role_revoke` | (사용자 관리 API 신설 필요) |
| `volume_create` / `volume_delete` | [app/api/admin/system.py](../app/api/admin/system.py) 볼륨 라우트 |
| `index_delete` / `index_clear_all` | [app/api/v1/file.py:clear_all_data / delete_index](../app/api/v1/file.py) |
| `db_source_upsert` / `db_source_delete` | [app/services/system_service.py:DBIngestionService.upsert_source / delete_source](../app/services/system_service.py) |
| `smb_source_upsert` / `smb_source_delete` | 동일 위치 SMBService |
| `cert_renew_run` | [app/api/admin/system.py:run_renew_script](../app/api/admin/system.py) |
| `auth_setting_change` (권한 dependencies 변경 등) | 라우터 변경 시 |

**구현 패턴**
```python
from app.core.database import write_audit_log
write_audit_log(
    actor=current_username, actor_role=current_role,
    action="db_source_upsert", target=source_name,
    status="success", ip=client_ip, user_agent=ua,
    detail=json.dumps({"id": row.id}),
)
```

**예상 작업량**: 1.5일 (지점 약 15개 + 테스트).

### B-3. audit_logs 보관기간 정책 + 아카이빙
**왜**: 무한 누적 시 DB 부담. 국정원 「개인정보의 안전성 확보조치 기준」은 접속기록 1년 이상 보관 권고.

**할 일**
- 보관기간 환경변수: `AUDIT_RETENTION_DAYS = 365` (기본 1년)
- 정기 cleanup 워커 또는 cron:
  - 운영 환경 분리 시 cron + alembic stamp
  - 또는 [app/services/worker_service.py](../app/services/worker_service.py) 확장으로 매일 1회 실행
- 삭제 전 콜드 스토리지로 export (선택): `audit_logs_archive_YYYYMM.csv.gz` → S3/MinIO/SMB
- 핵심 액션(`login_success`, `password_change`, `role_grant`)은 더 길게 보관(예: 3년) 옵션

**예상 작업량**: 1일.

---

### B-4. MFA 백업코드 + 관리자 리셋 절차
**왜**: M-4 의 TOTP 만 있으면 사용자 휴대폰 분실 시 영구 잠김. 운영상 회복 경로 필수.

**할 일**
1. **백업코드 발급**:
   - `/api/v1/common/auth/mfa/backup-codes` (POST, 자기 자신만)
   - 1회용 8자리 코드 10개 생성 → bcrypt/PBKDF2 해시로 저장 (`auth_mfa_backup_codes` 테이블)
   - 사용자에게는 평문 1회 노출 후 다시 볼 수 없음 (PDF 다운로드 권장)
   - 로그인 시 mfa_code 자리에 백업코드 입력 가능 → 매칭되면 해당 row 폐기
2. **관리자 리셋**:
   - admin 전용 `/api/v1/admin/users/{id}/mfa/reset` (POST)
   - `mfa_secret=NULL`, `mfa_enabled=False` 로 초기화 + audit (`mfa_admin_reset`)
   - 대상 사용자에게 알림 (이메일 미연동 시 로그인 후 재등록 안내)

**관련 표준**: NIST SP 800-63B "Authenticator Account Recovery".

**예상 작업량**: 1.5일.

---

### B-5. 관리자 사용자 관리 API
**왜**: 현재 사용자 추가/삭제/권한 변경/잠금 해제 API 가 없음. DB 직접 조작 또는 시드에 의존.

**할 일** — 신설 라우트 (`/api/v1/admin/users/...`):
| 메서드/경로 | 기능 | 필요 권한 |
|---|---|---|
| `GET /` | 사용자 목록 (활성/잠김/MFA 상태 포함) | admin |
| `POST /` | 사용자 추가 (정책 검증된 임시 비밀번호 + must_change_password=True) | admin |
| `PATCH /{id}/role` | 권한 변경 | admin |
| `PATCH /{id}/active` | 활성/비활성 토글 | admin |
| `POST /{id}/unlock` | 잠금 해제 (locked_until=NULL, failed_login_count=0) | admin |
| `POST /{id}/mfa/reset` | MFA 강제 해제 (B-4 와 함께) | admin |
| `DELETE /{id}` | 삭제 | admin |

**audit 통합**: 모든 액션이 audit_logs 에 기록 (B-2 와 결합).

**예상 작업량**: 2일.

## 2. UI/UX (관리자)

### U-1. 비밀번호 변경 강제 화면
**왜**: 백엔드는 `must_change_password=true` 응답을 주지만 프런트가 강제 흐름 미구현 → 사용자가 무시 가능.

**할 일**
- [static/admin/login.html](../static/admin/login.html) 의 로그인 성공 후 분기:
  ```js
  if (payload.must_change_password) {
      window.location.replace("/static/admin/password-change.html");
      return;
  }
  ```
- 신규 페이지 [static/admin/password-change.html](../static/admin/password-change.html):
  - 현재 비밀번호 + 새 비밀번호 + 새 비밀번호 확인
  - 클라이언트 정책 1차 검증 (서버와 동일 룰)
  - `POST /api/v1/common/auth/password` 호출 후 성공 시 /admin 으로

**예상 작업량**: 0.5일.

---

### U-2. MFA 등록 마법사
**왜**: 백엔드는 enroll/confirm API 만 제공. 사용자가 QR 코드를 스캔할 화면이 없음.

**할 일**
- [static/admin/mfa-setup.html](../static/admin/mfa-setup.html) 신규:
  1. `POST /mfa/enroll` 호출 → `secret`, `otpauth_url` 수신
  2. otpauth_url 을 QR 코드로 표시 (qrcode.js self-host 또는 SVG로 직접 그림)
  3. 사용자가 인증 앱 등록 후 6자리 코드 입력
  4. `POST /mfa/confirm` 으로 secret + code 전송
  5. 성공 시 사용자 설정 페이지로 복귀
- 로그인 1단계 후 `mfa_required=true && !mfa_enabled` 면 해당 페이지로 강제 이동(admin 정책)

**예상 작업량**: 1일 (QR 라이브러리 self-host 포함).

---

### U-3. 로그인 폼에 MFA 코드 필드
**왜**: 백엔드는 `mfa_code` 를 받지만 로그인 폼은 ID/PW 만.

**할 일**
- [static/admin/login.html](../static/admin/login.html) 에 MFA 입력 필드 추가 (초기 hidden)
- 1차 로그인 시도 → 401 + detail="MFA 코드가 필요…" 응답이면 MFA 필드 표시 + 자동 포커스
- 또는 응답 body 에 `mfa_required: true` 면 노출 (현재 응답 구조에 추가됨)

**예상 작업량**: 0.5일.

---

### U-4. 감사 로그 뷰어
**왜**: M-5 가 audit_logs 를 쌓지만 조회 화면이 없음 — DB 직접 조회로만 확인 가능.

**할 일**
- 백엔드: `GET /api/v1/admin/audit-logs?from=...&to=...&actor=...&action=...&status=...&page=...&size=...`
- 프런트: [static/admin/audit.html](../static/admin/audit.html) — 카드형 + 페이지네이션 + 필터(기간/액터/액션/상태)
- 메뉴 항목 추가 ([static/admin/menu.html](../static/admin/menu.html))
- CSV export 버튼 (선택)

**예상 작업량**: 1.5일.

## 3. 운영/배포 정책

### O-1. 백업/복구 정책 코드화 (L-1)
**왜**: 1차 점검에서 식별된 항목. 운영팀 합의가 선행되어야 코드 작업 가능.

**할 일**
- DB 백업 스크립트:
  - `pg_dump --format=custom` (PostgreSQL) / `mysqldump` (MySQL) 자동화
  - 일일 풀백업 + 시간별 WAL/binlog (선택)
- alembic version 동기 검증:
  - 백업 시점 alembic 헤드 기록
  - 복구 시 헤드 검증 후 적용
- 정기 복구 검증 (월 1회):
  - 임시 환경에 dump → upgrade head → 핵심 쿼리 smoke test
- OpenSearch snapshot:
  - `_snapshot` API 활용한 일일 스냅샷
- 보관/순환 정책: 일일 7일, 주간 4주, 월간 12개월

**관련 표준**: 국정원 가이드 — 백업 무결성 정기 검증.

**선결 사항** (운영팀 결정 필요):
- 보관 위치 (NAS/S3/MinIO)
- 보관기간 정책
- RPO/RTO 목표

**예상 작업량**: 협의 후 1~2일.

### O-2. CI 보안 게이트 통합
**왜**: H-8 에서 requirements 핀 적용. CI 에 자동화된 취약점 스캐너가 빠지면 의미가 약해짐.

**할 일** — `.github/workflows/security.yml` (또는 사용 중인 CI):
```yaml
- name: pip-audit
  run: pip install pip-audit && pip-audit -r requirements.txt
- name: bandit (정적 분석)
  run: pip install bandit && bandit -r app/ -ll
- name: secrets scan (gitleaks)
  uses: gitleaks/gitleaks-action@v2
- name: container scan (trivy, 선택)
  uses: aquasecurity/trivy-action@master
```
- pip-audit 실패 시 PR 차단 (CVE 발견 시 의존성 갱신 또는 예외 등록)
- bandit medium 이상 PR 차단

**예상 작업량**: 0.5일 + CI 시스템 접근.

### O-3. 운영 환경 시크릿 관리 표준
**왜**: 현재 `.env` 파일 의존. CREDENTIAL_SECRET 회전·롤백 시 운영 절차 미정의.

**할 일**
- 시크릿 저장소 결정 (Vault / AWS Secrets Manager / Azure Key Vault / 사내 KMS)
- CleverSearch 부팅 시 시크릿 로드 절차 문서화
- 키 회전 절차:
  1. 새 CREDENTIAL_SECRET 생성
  2. v3 prefix 추가 ([app/utils/crypto.py](../app/utils/crypto.py) 가 이미 버전 prefix 지원)
  3. 백그라운드 작업으로 모든 enc:v2:: row 를 enc:v3:: 로 재암호화
  4. 일정 기간 후 v2 키 제거
- JWT_SECRET 회전 시 영향 (모든 기존 토큰 무효 → 사용자 재로그인 필요) — 운영 가이드에 명시

**예상 작업량**: 협의 후 1일.
