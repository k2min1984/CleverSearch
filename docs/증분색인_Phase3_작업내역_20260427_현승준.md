## 3. 핵심 결정과 근거

### 3.1 `walk()` 반환을 NamedTuple `FileEntry` 로 — 위치 unpack 하위 호환

기존 `walk()` 는 `(rel, full)` 2-tuple 을 yield 했고 호출자(`for rel, full in walk()`) 가 위치 unpack 으로 받고 있었다. Phase 3 에서 size/mtime 을 추가해야 하는데, 4-tuple 로 바꾸면 기존 호출자가 즉시 `ValueError: too many values to unpack` 으로 깨진다.

- **선택**: `FileEntry(NamedTuple)` 로 (rel_path, full_path, size, mtime) 4 필드 정의.
  → 위치 0/1 은 그대로 (rel, full) 이지만, 4 원소 NamedTuple 이라 2변수 unpack 도 깨진다. **그래서 LEGACY 호출자 1곳을 `entry.rel_path`/`entry.full_path` 명시적 접근으로 변경**.
- 이렇게 하면 새 코드는 NamedTuple 이라 IDE 가 타입 인식하고, 위치 0/1 이 의미 그대로 유지되어 미래 호환성 보장.

**왜 dataclass 가 아니라 NamedTuple?**
- `for entry in walk()` 같이 단일 변수로 받는 흐름이 가장 자연스럽고, NamedTuple 은 인덱스 접근(`entry[0]`)과 attr 접근(`entry.rel_path`) 모두 지원.
- 메모리도 가벼워 walk 결과를 메모리에 쌓아둘 때 유리.
- 불변성도 NamedTuple 쪽이 명확.

검증: `FileEntry('a','/a',100,now)[0] == 'a'` 통과.

### 3.2 walk 결과 사전식 정렬

설계서 §5.4 "체크포인트 기반 재개" 의 전제 — "walk 순서는 사전식 정렬 보장 필요". 두 클라이언트 모두 `entries.sort(key=lambda e: name.lower())` 를 추가하여 디렉토리 단위 사전식 정렬을 보장.

**왜 이 위치?**
- 디렉토리 stack 자체를 정렬하면 깊이/폭 우선 순서가 꼬이고 의미가 모호해짐.
- "한 디렉토리 안의 파일들이 사전식 정렬" 이면, `cursor_value > "사전식으로 처리한 마지막 파일"` 비교만으로 재개 가능.
- 디렉토리 간 순서는 stack pop 순서(LIFO) 가 결정 — 같은 트리에서 같은 stack 시드면 결정적으로 같은 순서가 보장됨.

### 3.3 3단계 필터 (네트워크 read_bytes 최소화의 핵심)

설계서 §5.3 의 흐름을 그대로 구현 (`process_smb_job` 메인 루프):

```
단계 1: client.walk()                 → 메타(size, mtime)만 스트리밍, read_bytes 안 함
단계 2: _load_state_index() 1회 SELECT → file_index_states 메모리 dict
단계 3: 파일별 판단
  3-a. 로컬 없음                  → read_bytes → 색인 (신규)
  3-b. size&mtime 동일            → SKIP, read_bytes 호출 안 함 (★ 가장 중요)
  3-c. size/mtime 다름            → read_bytes → 해시 비교
       3-c-1. 해시 동일           → 색인 스킵, mtime/size 만 갱신
       3-c-2. 해시 다름           → 재색인
```

**왜 mtime 비교만으로 단정 짓지 않는가?**
- 일부 파일 시스템(SMB1, FAT) 의 mtime 정밀도가 1초 단위라 microsecond 차이만으로 변경 판정하면 오탐 빈발.
- DB 에서 가져온 `mtime` 과 walk 의 `mtime` 사이 1초 이내 오차는 동일로 처리 (`abs((s_mtime - e_mtime).total_seconds()) < 1.0`).
- size 까지 일치할 때만 SKIP — 둘 중 하나라도 다르면 read_bytes 후 해시 비교.

**왜 해시 동일 시도 색인 안 하나?** — 같은 내용을 OpenSearch 에 다시 보낼 이유가 없다. mtime 만 갱신해서 다음 walk 때 이 단계에서 SKIP 되도록 한다.

검증: `_is_meta_unchanged()` 5가지 시나리오 + 1초 이내 오차 흡수 통과.

### 3.4 SyncJob.cursor_value = "마지막 처리 파일 경로"

설계서 §5.4 그대로. 재개 시 walk 시작부터 cursor 까지 빠르게 skip(`if entry.rel_path <= cursor_value: continue`) → 그 이후부터 실제 처리.

**3-a 단계 (로컬 없음 = 신규) 의 read_bytes 가 비싸지 않나?** — 이 비용은 피할 수 없다. 신규 파일은 어차피 본문을 읽어야 색인 가능하므로. 핵심 절감은 "로컬 있고 안 바뀐 파일 = 전체의 95%+" 에서 read_bytes 를 안 하는 것.

### 3.5 배치 UPSERT — UNIQUE 제약 부재 대응

설계서 §5.5 는 `INSERT ... ON CONFLICT DO UPDATE` 를 권장하지만, 현재 `file_index_states` 스키마에 `(source_type, source_name, file_path)` UNIQUE 제약이 없다 — Phase 3 가 처음 추가하는 인덱스(`ix_file_state_lookup`) 도 UNIQUE 가 아닌 일반 인덱스다.

**선택**: ON CONFLICT 대신 **bulk SELECT → 있는 건 UPDATE / 없는 건 `bulk_save_objects` INSERT** 로 분기.

**왜 UNIQUE 제약을 안 만들었나?**
- 기존 데이터에 중복 row 가 있으면 UNIQUE 제약 추가가 실패한다 (운영 환경에서 부팅이 막힐 위험).
- 기존 LEGACY `_update_index_state` 도 SELECT-then-UPDATE-or-INSERT 였고, 운영 데이터 클린 상태가 보장되지 않는다.
- 추후 별도 마이그레이션에서 "중복 정리 → UNIQUE 추가 → ON CONFLICT 전환" 단계로 분리하는 게 안전.

**그래도 효과 보장**: chunk(300건) 단위로 한 번의 IN 쿼리 + 한 번의 commit 으로 묶이므로, **300건 = SELECT 1회 + UPDATE N회 + bulk INSERT 1회** 로 압축됨. 기존 row-per-file `db.add()` + `db.flush()` 보다 압도적으로 적은 쿼리 수.

### 3.6 메모리 dict 1회 로드의 트레이드오프

`_load_state_index()` 가 **소스의 file_index_states 전체** 를 1회 SELECT 해서 dict 로 올림.

- 장점: walk 도중 파일별 SELECT 가 0회. 100k 파일이면 100k SELECT → 1 SELECT (설계서 §5.8 "10만 쿼리 → 1 bulk SELECT").
- 비용: 메모리. 1행당 ~200 bytes 가정 시 100k 파일 = 20MB. 100만 파일이면 200MB. 운영에서 파일 수가 수백만이 되면 페이징 필요.

**현 시점 결정**: 메모리 단순함 우선. 수십만 단위면 충분히 안전. 운영 모니터링에서 RSS 가 위험 수준이면 페이징 도입(파일 경로 prefix 단위)으로 별도 처리.

### 3.7 OpenSearch `_id` = `{conn_type}:{source_name}:{rel_path}`

설계서 §5.5 "Upsert 키: `os_doc_id` (FileIndexState 저장값)". 같은 파일 경로는 항상 같은 `_id` 라 OpenSearch 가 자동 덮어쓰기 → DB 중복 체크 0회.

`conn_type` 까지 prefix 에 넣은 이유: 같은 source_name 으로 SMB/SSH 둘 다 등록될 가능성은 낮지만, 충돌 안전 마진. `FileIndexState.os_doc_id` 컬럼에도 같은 값 저장 → 추후 삭제/재색인 시 식별자로 사용 가능.

### 3.8 트랜잭션 분리 (Phase 2 와 동일 원칙)

| 단계 | 트랜잭션 |
|---|---|
| Job/소스 정보 로드 | 짧은 트랜잭션 1 |
| 클라이언트 connect (SMB/SSH) | 외부 네트워크만 사용 |
| `_load_state_index` (전체 1회) | 짧은 트랜잭션 2 |
| walk 루프 — read_bytes / index_bulk | 로컬 DB 미접촉 |
| pending_states 300건 차면 → 배치 UPSERT | 짧은 트랜잭션 3 (반복) |
| chunk 단위 진행률 commit | 짧은 트랜잭션 4 (반복) |
| Job 종료 — 이력 기록, last_seen_at, last_error | 각각 짧은 트랜잭션 |

긴 외부 작업 동안 로컬 DB 트랜잭션이 잡혀있지 않다 → lease 갱신/조회가 항상 즉시 통과.

### 3.9 LEGACY 보존 정책 일관성

Phase 2 와 동일 원칙: 기존 `SMBService.sync_source` 는 그대로 유지(주석에 LEGACY 표시 안 했지만 동작 보존). 새로 추가된 `enqueue_sync_job` 만 워커 경로를 사용. 스케줄러/관리자 sync 버튼은 LEGACY 그대로.

이번에 LEGACY 코드에 1줄만 손댐 — `for rel_path, full_path in client.walk()` → `for entry in client.walk(): rel_path = entry.rel_path; full_path = entry.full_path`. NamedTuple 4필드 변경에 따른 위치 unpack 호환성 확보 차원의 최소 수정.

## 6. DB 커넥션 / 네트워크 관점 — Phase 3 의 기여
