# CleverSearch 관리자 메뉴 쉬운 설명

작성일: 2026-09-30. 대상: http://127.0.0.1:8000/admin 의 **CleverSearch**. 현재 프로젝트의 화면과 서버 코드를 읽어 설명했다.

## 1. 스모크 실행과 결과 화면

### 무슨 일을 하나요?

자동차를 타기 전에 시동·불·브레이크를 짧게 확인하는 것처럼, 프로그램의 기본 기능 몇 가지를 자동으로 검사하는 버튼이다.

현재 검사 코드는 다음 일곱 묶음을 확인한다.

| 결과 이름 | 쉬운 뜻 |
| --- | --- |
| jwt_lifecycle | 로그인 → 로그인 상태 연장 → 로그아웃 → 로그아웃한 출입증 사용 차단 |
| rbac_viewer_restriction | 보기만 허용된 사람이 변경 작업을 하려고 하면 막는지 |
| dictionary_upsert_and_list | 사전 단어를 저장하고 다시 읽을 수 있는지 |
| scheduler_lifecycle | 자동 실행 기능을 켜고 끌 수 있는지 |
| dashboard_endpoints | 대시보드에 필요한 숫자와 상태를 읽을 수 있는지 |
| source_upsert_and_list | 파일/DB를 가져올 곳을 저장하고 다시 읽을 수 있는지 |
| ssl_status_and_script | 인증서 상태를 읽고 인증서 작업용 명령 파일을 만들 수 있는지 |

이 일곱 묶음이 통과해도 전체 웹 시나리오, 실제 회사 DB·SSO·LLM·메일, 장시간 사용까지 모두 통과했다는 뜻은 아니다.

### 왜 영어와 괄호가 많이 나오나요?

화면 코드가 검사 결과를 사용자용 문장으로 바꾸지 않고 **JSON이라는 개발자용 기록 형식**으로 그대로 보여주기 때문이다. `stdout` 안에 다시 JSON 문자열을 넣어 보여주므로 `\n`, `\"` 같은 기호도 보일 수 있다. 이 표시 자체만으로 고장이라고 판단하지 않는다.

| 표시 | 뜻 |
| --- | --- |
| status: success | 검사 프로그램이 통과 결과로 끝남 |
| status: fail | 하나 이상의 검사 실패 또는 검사 프로그램 실행 오류 |
| exit_code: 0 | 검사 프로그램이 정상 종료 코드를 반환함 |
| exit_code: 1 또는 다른 숫자 | 검사 실패나 실행 오류가 있어서 원인 확인 필요 |
| checks | 검사 항목 목록 |
| passed: true | 해당 항목이 기대한 대로 동작함 |
| passed: false | 해당 항목이 기대와 다르게 동작함 |
| stdout | 검사 결과와 일반 출력 |
| stderr | 오류·경고·진단 로그. 내용이 있다는 사실만으로 실패를 단정하지 않음 |
| HTTP 200 | 서버가 요청에 응답함. 응답 안의 검사 결과까지 통과했다는 뜻은 아님 |
| HTTP 401 | 로그인 정보가 없거나 유효하지 않음. 로그아웃 후 차단 시험에서는 기대값일 수 있음 |
| HTTP 403 | 해당 작업 권한이 없음. 보기 전용 사용자의 쓰기 차단 시험에서는 기대값일 수 있음 |

### 이번 결과는 왜 나왔나요?

사용자 메시지에 결과 캡처/본문이 첨부되지 않아 **이번에 어느 항목이 실패했는지는 아직 확정하지 않았다**. 서버 로그에서 스모크 실행 요청에 HTTP 200 응답이 있었음은 확인했지만 그 줄에는 검사 결과 본문이 없다.

다만 코드에서 다음 불일치를 확인했다.

1. 로그인 검사가 예전 고정 시험 계정 정보를 사용한다. 현재 로컬 계정 설정과 다르면 실제 관리자 로그인이 가능해도 이 검사는 실패할 수 있다.
2. 보기 전용 사용자 검사에서 읽기 성공(200)을 기대하는 옛 API 경로에, 현재는 라우터 전체의 운영자 이상 권한 조건이 걸려 있다. 그 검사는 권한 거부(403)를 받아 실패할 수 있다.

쉽게 말하면 **검사하는 사람이 옛날 열쇠와 옛날 검사표를 들고 왔을 가능성**이 있다. 결과의 `checks`, `passed: false`, `stderr`를 확인해 실제 원인과 대조해야 한다.

또한 이 버튼은 현재 설정을 물려받은 별도 프로그램에서 시험용 사전·소스를 저장하고, 스케줄러를 시작/중지하고, 인증서 작업 파일을 생성한다. 실행 코드는 자동 원상 복원을 하지 않는다. 그래서 단순히 상태만 보는 버튼과는 동작이 다르다. 이번 설명 작업에서는 재실행하지 않았다.

## 2. 전체 구조: 작은 도서관으로 생각하기

| 프로그램 용어 | 도서관에 비유하면 |
| --- | --- |
| 문서 | 책 |
| 소스 | 책을 가져오는 곳: 폴더나 DB |
| 수집 | 그곳의 자료를 읽어 오는 일 |
| 색인 | 책 내용을 빨리 찾도록 검색용 목록을 만드는 일 |
| 동기화 | 원본을 확인해 검색 자료에 반영하는 작업 |
| OpenSearch | 검색용 목록을 저장하고 찾아주는 검색 엔진 |
| 볼륨/인덱스 | 검색용 목록을 나누어 담는 보관함 |
| 사전 | 사람들이 쓰는 말을 검색기가 이해하도록 적어 둔 단어장 |

흐름: **폴더·DB의 자료 → 수집·색인 → 검색용 보관함 → 사용자가 검색**. 사전은 사용자가 입력한 검색어를 이해하는 데 도움을 준다.

## 3. 사전 관리

### 무엇을 하나요?

검색기에게 “이 말은 이렇게 알아들어”라고 알려 주는 단어장이다. 원본 문서 내용을 수정하는 기능은 아니다.

| 종류 | 쉬운 설명 | 예시 |
| --- | --- | --- |
| synonym / 동의어 | 함께 찾아볼 말을 알려 줌 | `AI → 인공지능`: AI를 검색할 때 인공지능이라는 말도 검색에 활용 |
| stopword / 불용어 | 검색에서 빼도 되는 말을 정함 | `그리고`를 등록하면 `계약 그리고 규정`에서 가운데 말을 제외 |
| user / 사용자사전 | 잘못 쓴 말이나 약속한 표현을 다른 말로 바꿈 | `계휙서 → 계획서`: 오타를 고쳐 검색 |

### 어떻게 쓰나요?

1. 종류를 고른다.
2. **원본 단어**에 사용자가 입력할 말을 넣는다.
3. 동의어/사용자사전이면 **대체 단어**를 넣는다. 불용어는 원본 단어가 기준이다.
4. **단건 저장**을 누른다.
5. 아래 목록에서 확인하고 검색창에서 직접 검색한다.
6. **수정**은 입력칸으로 값을 불러오며, 고친 뒤 다시 **단건 저장**해야 한다. **삭제**는 해당 규칙을 없앤다.

현재 코드 기준으로 동의어는 입력한 방향으로 확장된다. 양방향이 필요하면 각각 등록해야 한다. 불용어는 띄어쓰기로 나눈 단어와 정확히 일치할 때 빠진다. `는`을 넣었다고 `계약서는`의 끝부분을 자동으로 떼는 방식은 아니다. 검색어가 모두 불용어일 때는 원래 검색어를 유지하는 처리도 있다.

## 4. 데이터 수집/색인

### 4-1. SMB 색인 — 폴더의 문서를 가져오는 곳

회사 공유 폴더나 이 PC의 폴더에 있는 파일을 읽어 검색에 등록한다. 이 메뉴에서는 **SMB 공유 폴더, SSH/SFTP 서버, 로컬 폴더**를 설정할 수 있다.

- **신규 등록:** 어떤 폴더를 읽을지 이름·경로·필요한 접속 정보를 저장한다.
- **접속 테스트:** 그 폴더에 들어갈 수 있는지 확인한다. 파일이 모두 검색된다는 뜻은 아니다.
- **동기화:** 폴더 문서를 읽고 검색용으로 처리하는 일을 접수한다.
- **활성:** 자동 수집 대상으로 사용할지 정한다. 현재 처리 중이라는 뜻은 아니다.
- **이력:** 그 소스를 언제 처리했고 몇 건 성공했는지 확인한다.

현재 준비한 예시는 `수동검증_로컬폴더_20261001`이다. 이름에 SMB가 있어도 이 예시는 이 PC의 로컬 폴더를 사용한다.

**증분 모드**는 앞서 처리한 위치나 변경 기록을 이용해 추가 작업을 줄이는 방식이다. **전체 모드**는 처음부터 다시 확인하는 방식이다. 전체 모드라고 해서 원본 파일을 지우는 뜻은 아니다.

### 4-2. DB 색인 — 표에 들어 있는 글을 가져오는 곳

DB는 여러 표를 보관하는 큰 서랍장과 비슷하다. 게시판이라면 한 줄마다 글 번호·제목·본문이 들어 있다. DB 색인은 이 줄들을 읽어 검색에 넣는다.

| 입력 항목 | 쉬운 뜻 |
| --- | --- |
| 서버/포트 | 서랍장이 있는 주소와 들어갈 문 번호 |
| DB 이름 | 어느 서랍장인지 |
| 사용자/비밀번호 | 들어갈 때 쓰는 출입증 |
| 테이블/뷰 | 어느 표를 읽을지. 뷰는 필요한 내용만 보이도록 만든 표 형태의 창 |
| 컬럼 | 그 표의 어느 칸을 읽을지: 제목, 본문 등 |
| PK | 각 줄을 구분하는 고유 번호 |
| cursor / 증분 기준 | 어디까지 읽었는지 표시하는 책갈피 |
| chunk / 청크 | 한 번에 몇 줄씩 읽을지 |
| 대상 볼륨 | 읽은 내용을 어느 검색용 보관함에 넣을지 |

이번에 등록한 `CleverSearch_현재DB_문서데이터`는 이 PC의 `cleversearch_local` DB에서 문서 제목·본문·파일명을 읽는 설정이다. 등록 당시 연결과 6행 조회를 확인했고, 동기화는 실행하지 않았다. `id` 기준 증분은 새 번호의 행을 찾으므로 기존 행의 본문만 바뀐 것을 확인할 때는 전체 모드 등이 필요하다.

### 4-3. 통합 색인 이력 — 작업 접수표와 결과 일지

“부탁한 일이 접수됐나, 진행 중인가, 끝났나?”를 보는 메뉴다.

| 상태 | 뜻 |
| --- | --- |
| pending | 차례를 기다리는 중 |
| running | 처리 중 |
| done | 작업이 끝남. 실패 건수도 함께 확인 |
| failed | 오류로 작업 실패 |
| paused | 일시정지 상태 |
| skipped / 스킵 | 이미 같은 자료가 있거나 처리 대상이 아니어서 건너뜀. 반드시 오류인 것은 아님 |

- **맨 위 표:** 개별 작업의 접수번호(Job ID), 상태, 처리 건수를 본다.
- **아래 표:** 소스별 실행 요약과 메시지를 본다.
- **위 조회/아래 조회:** 각각 자기 표의 내용을 불러온다.
- **5초마다 자동 새로고침:** 진행 상황을 반복해서 읽는다.
- **이력 정리:** 오래된 기록을 지우는 기능이다. 검색 문서를 삭제하는 버튼과 다르다.

예를 들어 `색인 3 / 스킵 2 / 실패 0`은 세 건 처리, 두 건 건너뜀, 실패 없음이다. 접수 알림만 뜬 것으로 완료 판정하지 않는다.

현재 DB 워커의 하단 통합 이력 기록 방식에는 앞선 DB 등록 기록에서 확인한 후속 점검 항목이 있다. 상단 작업 상태와 하단 요약이 항상 동일하게 완비되어 있다고 보장하지 않는다.

### 4-4. 파일 감시 — 폴더 옆에서 변화를 지켜보는 사람

감시 중인 폴더에 파일이 생기거나 바뀌면 알아채고 자동으로 색인 작업을 한다.

- **행의 시작/중지:** 그 폴더 하나의 감시를 켜거나 끈다.
- **전체 시작/전체 중지:** 여러 소스의 감시를 함께 제어한다.
- **감시 중:** 변화가 있는지 지켜보는 상태다. 모든 파일 처리 완료라는 뜻은 아니다.

현재 실제 코드는 서버가 파일 경로로 직접 접근할 수 있는 폴더를 감시한다. 원격 SSH 주소만 등록했다고 원격 폴더를 직접 실시간 감시할 수 있는 것은 아니다.

또한 파일 삭제 감지 코드는 내부 변경 기록을 정리하지만 검색에 등록된 문서까지 삭제하지는 않는다. **원본 폴더에서 지운 파일이 검색에서도 자동으로 사라진다고 생각하면 안 된다.** 이 내용은 화면 소개보다 실제 구현 범위가 좁은 부분이다.

### 4-5. 네트워크 — 연결 상태를 확인하는 사람

검색 엔진, 프로그램의 기본 DB, 활성 파일 소스에 연결할 수 있는지 주기적으로 확인한다.

- **시작/중지:** 연결 확인을 켜거나 끈다.
- **감시 간격:** 몇 초마다 다시 확인할지 정한다.
- **상태 확인:** 확인 기능이 작동 중인지 본다.
- **조회:** 끊겼거나 다시 연결된 기록을 본다.
- **disconnect:** 연결 끊김.
- **reconnect_attempt / reconnect_fail:** 다시 접속해 보았지만 아직 안 됨.
- **reconnect_success:** 다시 접속됨.
- **JSON / 리스트 전환:** 같은 기록을 개발자용 글 또는 표로 바꿔 본다.

이 메뉴가 공유기나 서버 고장을 모두 자동 수리하는 것은 아니다. 현재 DB 점검 대상은 앱의 기본 DB이며, DB 색인에 등록한 모든 외부 DB를 각각 점검하는 구현은 아니다. 상태 변화가 없으면 이벤트 목록이 비어 있을 수 있다.

### 4-6. 스케줄러 — 시간을 맞춰 일을 시키는 알람시계

“이 폴더는 한 시간마다, 저 DB는 하루마다 확인해”라고 예약한다.

- **동기화 주기:** 확인 간격.
- **다음 실행:** 다음 예약 시각.
- **마지막 실행:** 마지막으로 작업을 수행한 시각.
- **행의 활성 상태:** 그 예약을 사용할지.
- **스케줄러 시작/중지:** 예약을 처리하는 전체 기능을 켜거나 끔.

활성 소스는 기본 24시간 주기로 등록되도록 되어 있다. 시작 버튼은 예약 기능을 켜는 것이며, 모든 문서를 즉시 처리 완료하는 버튼이 아니다. 예약 시각이 되어야 해당 작업이 실행된다. 서버 프로그램이 꺼져 있으면 예약 작업도 실행되지 않는다.

## 5. 시스템/보안

### 5-1. 볼륨 관리 — 검색용 보관함 관리

OpenSearch에 검색 자료를 담을 보관함을 만든다. 회사 공지와 다른 자료를 서로 다른 인덱스로 나누는 데 사용할 수 있다.

| 항목/버튼 | 쉬운 뜻 |
| --- | --- |
| 인덱스 이름 | 보관함 이름 |
| 샤드 | 큰 보관함을 나눈 조각 수. 현재 화면에서는 생성할 때 정함 |
| 레플리카 | 고장에 대비한 복제본 수. 원본 오삭제를 복구하는 백업과는 목적이 다름 |
| Alias | 앱에서 보관함을 참조할 때 쓰는 별명 |
| 권장값 채우기 | 입력칸에 기본 숫자를 넣음. 생성까지 하는 것은 아님 |
| 볼륨 생성 | 실제 검색용 보관함을 만듦 |
| 목록 새로고침 | 현재 저장된 목록을 다시 읽음 |
| 수정 | 별명·복제본 수 등을 바꿈 |
| 삭제 | 해당 검색용 보관함의 삭제에 영향을 주는 작업 |

보관함을 새로 만들었다고 문서가 자동으로 채워지지는 않는다. 자료를 넣는 소스의 대상 설정과 실제 색인이 이어져야 한다.

### 5-2. SSL 관리 — 사이트의 신분증과 유효기간 관리

인증서는 사이트의 신분증 같은 것이다. HTTPS 연결은 브라우저와 서버 사이의 내용을 암호화해서 주고받게 한다.

- **인증서 상태:** 인증서 파일의 유효기간과 남은 날짜를 확인한다.
- **경고 기준일:** 만료가 며칠 이내로 남으면 주의 표시할지 정한다.
- **갱신 스크립트 생성:** 인증서 작업을 할 명령 파일을 만든다.
- **갱신 스크립트 실행:** 그 명령 파일을 실제로 실행한다.

현재 코드가 생성하는 것은 **localhost용 자체 서명 인증서를 만드는 OpenSSL 스크립트**다. 화면에 Let's Encrypt 안내가 있어도 회사 도메인의 공인 인증서 자동 갱신까지 구현·검증됐다는 뜻은 아니다. 인증서를 만들기만 해서는 실행 중인 서버가 자동으로 HTTPS로 바뀌지 않는다. 서버에 적용하는 설정도 필요하다.

현재 관리자 주소는 `http://127.0.0.1:8000`이다. SSL 메뉴가 있다는 이유로 주소를 `https://`로 바꿔 접속할 수 있는 것은 아니다.

### 5-3. 초기화 — 검색 자료와 기록을 비우는 지우개

시험을 마친 뒤 자료를 정리할 때 쓰는 삭제 기능이다.

| 버튼 | 현재 코드가 지우는 범위 |
| --- | --- |
| 전체 데이터 초기화 | 설정된 기본 검색 인덱스 안의 문서 + DB의 문서 목록·검색 로그·최근 검색어 |
| 인덱스 완전 삭제 + DB 초기화 | 기본 검색 인덱스 자체 + 위 세 종류의 DB 데이터 |

첫 번째는 보관함 안을 비우고, 두 번째는 보관함 자체도 없애는 것에 비유할 수 있다. 현재 코드가 회사의 모든 DB와 PC의 원본 폴더를 통째로 지우는 기능은 아니지만, 삭제된 검색 자료·기록은 이 화면에 실행 취소 기능이 없다. 메뉴를 열어 내용을 보는 것과 버튼을 눌러 실제 삭제하는 것은 구분해야 한다.

## 7. 이번 설명 작업의 기록

- 실제 메뉴·화면 JavaScript·관련 서버 코드를 읽음. 스모크를 새로 실행하거나 앱/DB 설정을 변경하지 않음.
- 캡처 미첨부로 사용자의 실제 스모크 실패 항목은 미확정. 첨부 요청 후 확인 대기.
- 확인한 구현 차이: 스모크 고정 로그인/옛 권한 기대값, 파일 감시의 원격·삭제 반영 범위, 네트워크의 기본 DB 감시 범위, SSL의 localhost 자체 서명 생성 범위. 설명에 반영했으며 이번 설명 작업에서 수정한 것으로 기록하지 않음.
- 주요 근거 파일: `scripts/run_system_smoke_tests.py`, `static/admin/dashboard.html`, `static/admin/menu.html`, 각 메뉴 HTML, `app/services/dictionary_service.py`, `app/services/system_service.py`, `app/services/db_service.py`, `app/api/user/file.py`, `app/api/admin/system.py`, `app/main.py`.
